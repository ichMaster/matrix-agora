# Architecture — matrix-agora

## Overview

Two small axes bound by one agent codebase. **The agents' capabilities** grow: echo → Gemini replies → turn-taking → canon + session memory → world awareness (place, clock, day memories, plans, the hourly today block) → token accounting. **The operations surface** grows separately: terminal processes on the Mac first, then Docker images with CI behind them and deployment to the Ubuntu server, and finally the **panel** — the point of the whole project — served from that server. The panel manages **simulations** (environments agents join; the chat — the homeserver and the room — is the first and only one here) and the agents connected to them. Everything the agents do rides on the plain Matrix client-server API.

## Components

- **Homeserver:** [Continuwuity](https://continuwuity.org) — a Matrix homeserver in Rust: one Docker container, embedded RocksDB, no Postgres. `server_name = agora.lan` is only the domain part of user ids (`@ada:agora.lan`); clients connect to `http://192.168.1.197:8008` directly, so no DNS is needed. Federation and encryption are disabled; registration is open (token-gated) only during setup, then closed. The compose file is the deliverable of ROADMAP v0.1.
- **Client:** Element Desktop on the Mac. Specifically Desktop, not app.element.io — the web version runs over HTTPS and will not connect to an HTTP homeserver on the LAN (mixed content).
- **Agents:** the same `agents/agent.py` with different TOML configs (account, canon, simulation). Libraries: `matrix-nio` + `google-genai` (async `client.aio.models.generate_content`, model `gemini-2.5-flash`). **Each agent is its own Docker container** — one compose service per agent — on the Ubuntu server from v3.2; `uv run` on the Mac remains the dev mode. The names "Ada" and "Bruno" are placeholders. From v4.1 a reply goes through the **responder seam** (`agents/responder.py`: `Turn` → `Reply(text, finish)`), chosen by the TOML's `engine`; `gemini` (`GeminiResponder`) keeps this contract exactly, and later engines plug in behind the same interface.
- **Panel (from v3.3):** the product of the project — a Docker container beside the homeserver: a FastAPI JSON API plus one static vanilla-JS page, `:8090`, LAN-only behind ufw, Bearer `PANEL_TOKEN`. It manages **simulations** through a declarative registry (the chat is the only entry) and the agents connected to them, via the local docker socket and the `state/` mount (§The panel).
- **Deployment:** the repo is the source of truth. `server/deploy.sh` (v0.2) syncs `server/` to the Ubuntu host and applies the whole stack — homeserver, panel, one container per agent — with `docker compose pull && up -d`; the images come from GHCR, built by CI (§Deployment and CI/CD).
- **Storage:** the gitignored `state/` directory — at `~/matrix-agora/state/` on the server in production (from v3.2), local on the Mac in dev mode — bind-mounted into the agent containers and the panel. Each agent's Matrix session, memory files, day memories, plans, today block, usage log, lock and logs. There is no database (§Data and state files).

## Message flow and the allowlist

The invariants every reply path must honor:

1. **Login once, then the token.** First run logs in with the password and saves `access_token` + `device_id` to `state/<name>.json`; later runs restore them. Logging in with the password on every start would create a new device on the server each time.
2. **Invites:** join only invites from `OWNER` into `ROOM_ID`. Ignore or leave every other invite. **From v5.6** a
   person with the `private` capability also joins the owner's invite into **one** private room besides Agora — the
   first, or the same one again (`should_join_invite`); its id is kept in `state/<name>.private.json`. The stored
   room counts only while the owner is still in it (`live_room`, v5.6 review #2): when he left it, a new invite
   of his replaces it and the old room is left.
3. **Start without the past:** the first `sync` is used only to obtain `next_batch` and its events are **not processed** — otherwise a restarted bot replies to the whole room history. After that, `sync_forever`. **Context survives a restart (from v2.2):** right after the first sync the agent fetches the last `HISTORY_N` messages of `ROOM_ID` once from the server (`/messages`, backwards) and seeds its context window and the turn-taking timeline (with event ids, and the owner's latest message) with them, in chronological order — **never replying to any of them** and never adding them to the session timeline (they were already summarized). Nothing is stored locally; the room itself is the source.
4. **Message filter** (`RoomMessageText` only — edits, notices and other event types never trigger a reply). Handle a message only if all hold:
   - `room.room_id == ROOM_ID`;
   - `event.sender != own user_id`;
   - `event.sender ∈ {OWNER} ∪ the roster's other members` — an **allowlist in code**, like `LUMI_TELEGRAM_ALLOWLIST` in Lili. A herald (v5.1, Hermes) is never in it: he takes no part in the talk, so a line from him would be ignored (`speakers` in `agents/roster.py`). The **roster** (from v4.1) is the simulation's `agents` list in `simulations.toml` plus each listed `agents/<name>.toml` (`agents/roster.py`); every image ships the same files, so every agent sees the same roster — shared input, never shared state.
   Everything else is logged as `ignored`.
   **The private chat (v5.6, `private`):** a message in the agent's own private room is handled only from the
   owner (`Verdict(True, "private")`); any other sender there is `sender-not-allowlisted`, and every other room
   stays `foreign-room`. A private message is answered outside Agora's turn-taking (no wave, no roll), in voice
   under the speakers' rules, from a prompt with the private brief and the private chat's own history — never
   Agora's. Its lines join the person's session labelled «… (наодинці)», so the summary, the day's journal, the
   day memory and the plans know them; her Agora prompt carries the discretion line (what was said privately is
   never retold or hinted at). After `PRIVATE_IDLE_S` of private silence, within `PRIVATE_HOURS`, at most
   `PRIVATE_NUDGES_PER_DAY` a day, she writes first (`private_nudge_due` — the cat's `nudge_due`). Hermes, the
   recording and the other agents never see the private room (`agents/private.py`).
   **Telegram, the private chat's second door (v5.7, `telegram`):** the person's own bot, polled by her own process
   beside the sync (`agents/telegram.py`: `getUpdates` long polling from the offset in `state/<name>.telegram.json`,
   saved after every batch, so an update is never answered twice; outbound HTTPS only). Only the owner's numeric id
   (`TELEGRAM_OWNER_ID`) in a private chat is handled (`allowed`); a stranger, a group, an edit or another kind is
   logged `ignored: <reason> (telegram <kind>)`, never an id or a word. **The owner's commands (v5.14, pinned by
   `tests/test_telegram_commands.py`):** a «/» text of his, sent after the start, is `telegram_command`'s and never a
   line of her talk — `/status` (the route in the commands' own words — `auto: gemini`, `auto: backup до 14:05`,
   `backup (закріплено о 21:27; скасувати: /auto)`; the blocks in the last hour and today out of `FALLBACK_DAY_MAX`;
   her private chat's lines waiting for the judge and censored; today's answers by gemini and by backup — the day's
   counts from her usage lines (`day_counts`: the answer kinds, `blocked`, the engine), never only since the route's
   file began; `status_text`, `agents/route.py`), `/auto`, `/gemini`, `/backup` (a pin, through `route_step`), and
   any other the list (`COMMAND_HELP`); without the backup a pin says it is off. **`/purge`** (the owner, 2026-10-30)
   answers with how many lines and facts would go and waits for `/purge yes` within `PURGE_CONFIRM_S` (120 s); then
   `purge_backup_talk` deletes the backup's talk — `Archive.purge_closed` (every private line `waiting` or
   `censored`, with its FTS row), `purge_closed_facts` (the facts with such a mark; the archive's mirror follows),
   and those lines in her history — the one exception to «nothing lived is deleted»; the log names the counts only;
   her usage lines and logs (no text) stay, as do Telegram's own copy of the chat and the Element room. The answer is one ⚙️ service line,
   text only, never voiced; a command and its answer never reach her history, the archive, the facts, the session or
   a prompt, and never reset her writing-first timer; logged by the command's name only. A command from before the
   start stays `ignored: command`. With `fallback` the list is registered at start for his chat only (`setMyCommands`,
   `BotCommandScopeChat`). **The first-sync rule holds there too:** what
   the owner wrote before this start is read into the private history as context and never answered. A text, or a
   voice note heard by her own Deepgram client (capped download, in memory only, an `stt` usage line; not heard → a
   fixed short line, no model call), takes the same path as an Element private message (`private_line`): **one
   history, one memory** labelled «наодинці», one pending answer that coalesces across both doors. The answer goes
   back to the door of the owner's latest message (`pick_door`; the other open door when that one is closed): in
   Telegram always a voice note in her own voice (`send_voice`, OGG/Opus), then the same text (`send_message`), under
   the speakers' monthly budget, with «recording voice…» kept up while she composes. She writes first through the door
   he used last (`last_channel` in `state/<name>.private.json`), or always through one door when `PRIVATE_FIRST_DOOR` says so (v5.8.2, the owner: Кіра — always Telegram; a closed door falls back to the other). A refused token (401/404) stops only the poller; 429
   waits `retry_after`; anything else backs off from 5 s, doubling, to 5 min — Agora and Element never notice.
   **Voice (v5.2): one transcript, shared by every agent.** No agent answers audio: an owner's `RoomMessageAudio` in
   `ROOM_ID` is remembered (its event id, RAM, the last 200) and logged as `ignored: audio (transcribed by Hermes)`;
   any other audio is `ignored`. The roster's `transcribe` member (Hermes) posts «🎙 Ich: …» as a reply
   (`m.in_reply_to`) to that voice event (`transcript_content`). `transcript_of` — the transcriber's, not an edit,
   with the prefix, replying to a remembered owner voice — makes it **the owner's own message**: the sender `OWNER`,
   the text after the prefix, the transcript's event id and time; so the history and timeline read «Ich: …», R1, the
   group address and the fallback choose as for the typed words, and the session (the journal, the memories) holds
   it. The backfill seeds it the same way. Any other line of his stays `sender-not-allowlisted`.
5. **Typing:** `room_typing(room_id, True)` before the Gemini call and `False` after it, reset in a `finally`.
6. **Send as `m.text`**, never `m.notice` — the other agent might treat a notice as a service message.
7. **On a failed or empty Gemini reply:** log the error, send nothing, keep running. The bot never crashes on a model failure.

Keep the decisions pure: the filter, mention detection, the ranking, `wave_count`, who-replies, transcript and prompt assembly are functions over plain data, so tests need no nio objects and the nio callbacks stay thin adapters.

## Turn-taking and loop protection

The agents see each other, so without rules they would reply to each other endlessly. From v4.1 the rules hold for any number of agents. Every agent derives every decision from the same inputs — the server-assigned `event_id`, the shared room timeline and the roster — so they agree **without any shared state or coordination**; never add any. The functions are pure (`agents/turns.py`), with the rng and the clock injected.

**The ranking.** `rank(event_id, members)` is weighted rendezvous (highest-random-weight) hashing: `u = (sha256(event_id + "\n" + localpart)[:8] + 1) / (2⁶⁴ + 1)`, `score = −weight / ln(u)`, highest first. The same event gives the same order on every machine (`hashlib`, never Python's salted `hash()`); a member's share of first places follows its `[turns] weight`; different events give different orders.

**Modes** (the TOML's `[turns] mode`; from v5.1 `none` — a herald's, forced by his type, in no pool: naming him chooses no one, the group address and the ask move leave him out, and his user id is never answered): `ranked` takes part in R1 and R2 (Ada and Bruno; from v4.5 Claude — weight 1, the owner's choice; 0.4 from 2026-10-13, so Ada and Bruno talk more); `mention-only` answers only when named (or on a group address); `ambient` (v4.2, the cat) is never chosen by R1 or R2 — named it always answers — by the owner in words; by an agent (from 2026-10-11) it always reacts, from 2026-10-13 with a purr by `CAT_PURR_P` and otherwise in words under the wave limit (the owner: the agents ask him so often that he talked all the time and hardly purred); otherwise it reacts to any allowlisted message on its own deterministic draw (`uniform(event_id, "react:"…) < CAT_REACT_P`), and a reaction is a **purr** with `CAT_PURR_P` (`uniform(event_id, "purr:"…)`).

**Purrs (v4.2).** A purr («Мрррр.», «Мур.», «*потягується*»…, `is_purr`) is produced in code at zero tokens. Every agent marks it in its timeline entry `(name, ts, event_id, purr)`: a purr is not counted by `wave_count`, never produces an R2 candidate, and is transparent to R3's "still the latest" and to the fallback; consecutive purrs collapse in the context window and the session. A spoken ambient reaction to an agent message obeys the wave limit; one to the owner counts but is never stopped, and is reserved in the wave like R1's answers (`owner_speakers` — every agent computes the cat's draw from the event id and the shared settings). The cat's spoken lines are capped at `CAT_MAX_WORDS`. Only the owner's message is never a purr (v4.2 review #2), and in `pending_answers` any line arrives — the cat's purr-worded spoken answer releases his reservation (v4.2 review #13) — so he never purrs while his own words are on their way (v4.3 review #1).

**The initiators (v4.3, v4.5).** Every agent answers; only an agent with an initiative capability ever posts without a trigger — the cat's `nudge` (v4.3) and Claude's `news` (v4.5), each held by at most one member of a simulation. His idle watcher checks the pure `nudge_due(now, local now, last room message, last attempt, today's count, …)` (`agents/nudge.py`): after `CAT_NUDGE_IDLE_S` of room silence (purrs included; counted from the later of the last message and the agent's start, so a restart never nudges at once — review #9), at least that long after his last attempt, under `CAT_NUDGES_PER_DAY`, within `CAT_NUDGE_HOURS` (local, start inclusive, end exclusive; a start after the end wraps past midnight — `09-03`) — and never while a reply of his is on its way. `nudge_kind(day, n)` picks `memory` (a past-life thesis via `pick_memory` over the recent talk, never verbatim), `command` (a Linux line, text only) `horoscope` (the day's reading as a metaphor; `memory` when there is no mood today) or — the owner, 2026-10-11 — `telegram` (a sysadmin joke for the room's assistant, Claude: framed like a ham-radio telegraph message, «CQ CQ КЛОД DE КІТ» … «73 SK», the joke itself in plain Ukrainian, up to 45 words; named, so he may answer; `memory` when there is no assistant) from `uniform("<day>:<n>", "nudge")`. One model call (kind `reply`): his prompt plus the material and the nudge rule, the last `HISTORY_N` lines as the transcript, then the reply's checks (trim, `clean_reply`, PASS, the word cap, duplicate, `outs_a_persona`) and a pre-send check that the room is still quiet. Every attempt is recorded in `state/<name>.nudge.json`; only a sent nudge counts. A nudge is an ordinary agent message: the silence has emptied the wave window, so the others take it by R2 — one next speaker under the usual limits.

**Claude's news (v4.5, the `news` capability of an `assistant`; the owner, 2026-10-11).** Every `CLAUDE_NEWS_EVERY_S` (3600 — every hour, not after an hour of silence: the cat's 20-minute nudges kept the room from ever being that quiet, review #6), once the room has been quiet for `CLAUDE_NEWS_IDLE_S` (300; never less than `BOT_WINDOW_S`), at most `CLAUDE_NEWS_PER_DAY` (24), within `CLAUDE_NEWS_HOURS` (`09-01`) — `nudge_due` with its `gap_ms`, checked by his idle watcher, never while a reply of his is on its way. **The source is The Guardian only** (`agents/guardian.py`, as in Lumi): one SDK call with `CLAUDE_NEWS_BRIEF` (`agents/logic.py`) and only two tools, `search` (the newest articles for an English query, a section, ≤ 14 days) and `read` (an article's text by its content id, never a URL), served in-process (`claude_sdk.guardian_server`, the SDK server `guardian`) — no built-in tool, no web search; the guard allows exactly `mcp__guardian__search` / `mcp__guardian__read`, and the init check those two (plus the CLI's MCP resource tools, which the guard refuses) and the server `guardian`, only on a news call — a mismatch there refuses that call only, never his replies (a wrong auth source still blocks him). The key (`GUARDIAN_API_KEY`, in `server/claude.env`) is taken out of the environment at start, so the CLI never inherits it, and never reaches a prompt, a tool result or a log (an HTTP error is logged by its type: its text carries the URL). The brief: find a fresh article bearing on what the room has been talking about in the last `HISTORY_N` (40) lines, tell it in 1–3 Ukrainian sentences with its link, or `PASS` when nothing fits; no `GUARDIAN_API_KEY`, no news (logged at start); then the reply's checks and the same pre-send check that the room is still quiet. Every attempt is recorded in `state/<name>.news.json` (the nudge state's shape); only a sent item counts. Like a nudge it is an ordinary message the others may take by R2.

1. **R1 — the owner's message:**
   - names one or more agents (any of their `name_forms`, whole words, or their Matrix id) — **exactly the named agents** reply; the named one replies immediately;
   - addresses everyone («всі», «усі», «всім», «усім», «кожен», «кожна», «кожному» in an addressing position: the start of the message, right before `,` `!` `?` or its end, or after «ви»/«вам») — **every ranked and mention-only member** replies;
   - names no one — the top `OWNER_REPLIERS` (default 2) of `rank(event_id, ranked members)` reply, each after a random delay of 1–`REPLY_DELAY_S` s (default 4), so they don't speak at once and the second sees the first's line in history;
   - answers to the owner are never stopped by the limit, but they count toward it.
2. **R2 — an agent's message M:** at most **one** candidate: among the members M names (ranked or mention-only, never its sender), otherwise among the ranked members other than its sender — the top of `rank(M.event_id, …)`; when M names only an ambient member (the cat), there is no candidate — he answers it himself (v4.5 review #3); nor when it names only the owner («Ich», `OWNER_FORMS`) — a question to him waits for him (v4.6 review #1). The candidate replies if the wave is below `MAX_BOT_TURNS` (default 3) and — when M does not name it — a roll passes `BOT_REPLY_P` (e.g. 0.5). **An address is always answered** (the owner, 2026-10-11; before, naming decided who, not whether): a named candidate skips the roll, never the wave limit.
   - **The wave** = `wave_count`: agent messages since the owner's last message **within the last `BOT_WINDOW_S`** (default 600 s), counted by server timestamps, **including M**, plus the owner's chosen answers still on their way (`pending_answers` — every agent computes R1's choice for the owner's latest message, so an agent-to-agent reply never overtakes them; an agent never reserves for itself, and a reservation lapses `FALLBACK_S` after the owner's message, so a chosen agent that passed, failed or is away never holds the wave; when a reservation is what blocks, R4 resumes at its lapse). v1.2's `bot_streak` excluded M, so the same behavior needs `MAX_BOT_TURNS` + 1. An owner message resets it.
3. **R3 — the re-check at fire time** (agent-to-agent replies only): after the delay, before the model call and again before sending, M must still be the room's latest message and the wave still below the limit; otherwise the reply is dropped (`silent: moved on`). A newer message for the same agent — an owner message that chose it, or an agent message that makes it the candidate — coalesces into the pending reply and becomes what it answers; if it arrives during generation and the stale reply is dropped, the pending reply gets one more pass with fresh context, so an owner message is never swallowed; an owner message that coalesces after a reply has read its context gets its own pass even when that reply is sent (v4.5 review #4 — a slow answer to the owner no longer swallows his next question).
4. **R4 — a rate, not a lock:** a candidate blocked by the limit pauses until the window frees (the oldest counted turn ages out) and then re-evaluates — only if nothing newer arrived meanwhile; a resumed decision always rolls `BOT_REPLY_P`, named or not (v4.5 review #2 — two agents naming each other would otherwise never stop). So the agents talk in bursts of at most `MAX_BOT_TURNS` per window until `PASS` or the probability gate ends the exchange; the owner never has to restart it (owner, 2026-10-10: background waves stay).
5. **The fallback:** if no agent has answered an unnamed, non-group owner message within `FALLBACK_S` (default 30), the best-ranked ranked member that R1 did not choose answers. Each agent checks for itself from the timeline; busy with another reply, it re-arms briefly instead of giving up, and it re-checks right before sending, so a slow chosen answer that lands meanwhile is never doubled.
6. **`PASS`:** if the model returns exactly `PASS` (tolerating surrounding whitespace), send nothing. The prompt must explicitly allow this. A `PASS` on its own line or at the very end of a longer reply is dropped and the rest is sent; nothing of its own left → nothing is sent — the sentinel never reaches the room (pinned by `tests/test_turns.py` and `tests/test_first_sync.py`).

## Voice messages (v5.1)

  - **Time moves the story:** as real dates pass, a future chapter becomes the current one, so life events written for 2027 or 2030 start happening in the agents' days when those years arrive.
  - **Dated events (v5.11):** a chapter may hold a `### Події` subsection, one line per event: `- YYYY-MM-DD[ HH:MM] · known|surprise · one sentence`. An optional local time (review #4) makes the event fall at the first tick from that time, told at that time, and the plans show it («о 19:00»); without one it falls at her day's first tick. A time outside `EVENT_HOURS` is warned about at startup, since it would never fall. The subsection runs to the next heading or the chapter's end, and `parse_life` cuts it out of the chapter's body (`Chapter.events`), so no prompt that shows the chapter shows the list. A malformed line, an unknown kind or a date outside the chapter's years stops the agent at startup (`LifeError`).
    - Only code reads the list: `events_due(story, day)` delivers an event on its date (known or surprise) into the events layer (§Memory), and `known_ahead(story, today, until)` gives the plans the **known** events ahead.
    - **A surprise never reaches a prompt before its date**, like a future chapter.
    - Кіра's list (drafted by Claude, edited by the owner) lives in her private life story.

## Memory

- **Context window:** each agent keeps the last `HISTORY_N` (40 from v4.1) room messages in RAM — its own and the other agents' included — and passes them to the model as one text, one `"Name: text"` line each. Raw history never persists locally; after a restart the window is re-seeded from the room on the server (§Message flow, rule 3).
- **The waiting mark and the backup's readers (v5.14).** A line closed to Gemini (`GEMINI_CLOSED`: `waiting`, `censored`) stays in the archive and in her private history: the backup reads every mark — `search_words`, `lines`, `around` and `latest` take `gemini=False` — while Gemini's readers, `vectors` and `unembedded` never return one. Her history stays `(speaker, text)`, with `_closed` beside it, the pairs closed to Gemini (filled from the archive's marks at start): `gemini_history()` leaves them out — conservatively, a same text open elsewhere too — and a closed line leaves the session (its summary, its facts and the day journal are Gemini's). A block or a refusal on her private answer marks the snapshot's lines `waiting` (`mark_unanswered`; v5.13 marked them `censored` and dropped them from her history).
- **The censored mark (v5.13, the owner: «я хочу щоб модель якось сама позначала такі меседжі»).** When Gemini blocks or refuses her private answer (`agents.llm.LAST_BLOCK`, a `ContextVar` the client sets on a block or a refusal and clears at each answer's start, so a concurrent call never sees another's), the owner's lines that answer was given — those since her last answer, taken as `(key, text)` just before the call, so a line that comes while she composes is never marked and stays to be answered (code review #2) — are marked `censored` (`Archive.censor`: the mark set, the vector dropped) and leave her in-memory history and the session — so no later Gemini call (an answer's history, the recall, «Agora today», the reflection, the session summary, the facts, the day journal, the facts seed) gets them, and they are never embedded again: every reader of the archive (`search_words`, `vectors`, `lines`, `around`, `latest`, `unembedded`) skips `GEMINI_CLOSED`. A line she writes first has no new message, so its block marks nothing; an Agora line is held by every agent, so a block there marks nothing either (v5.14's scope). The log names the stage and the count, never a text.
- **The archive (v5.8, a person with `recall`; Кіра; the owner, 2026-10-25, lifting the non-goal for her).** Modelled on Noos's `memory/sessions.db`: `state/<name>.archive.db` (`agents/archive.py`, SQLite, 0600) keeps every line she sees — every Agora line (live, and the restart backfill), both sides of her private chat through both doors — with its key (the Matrix event id, `tg:<update_id>`, or her own), time, place (`agora` / `private`; `facts` from v5.8's facts), channel and speaker. Append-only, never pruned; a key held already is a no-op. An FTS5 index (`unicode61`) makes a line searchable by words at once; the idle watcher adds Gemini embeddings (`gemini-embedding-001`, 768 floats, `RETRIEVAL_DOCUMENT`) to up to `EMBED_BATCH` (100) lines a tick, a failure waiting for the next tick. A recall fuses the BM25 list and the cosine list (50 each, numpy — the vectors read from the file once and kept normalised in memory, appended as lines are embedded and read again only when the facts change: v5.8 review #5) by reciprocal rank fusion (k = 60) — `fuse`, `cosine_top`, `pick_recall` are pure. **The first fill** (an empty archive at start, beside the sync): Agora's last `ARCHIVE_AGORA_LINES` (1,500) lines and the whole private room (bounded at 5,000 events) from the homeserver; Telegram keeps no history to fetch. **At every start** the private history comes from the archive's last `HISTORY_N` private lines, both doors, so a Telegram line survives a restart (v5.7 code review #5). No other agent reads the file, and no text from it reaches a log. Everyone else's long-term memory stays the layered digests below.
- **Facts about the owner (v5.8, a person with `facts`, which needs `private`; Кіра).** Noos's `memory/facts/` format (`agents/facts.py`): `state/<name>.facts/`, one Markdown file per fact — `pin` (1 always in her private prompt, 2 while there is room, newest first within a pin, so past the limit a fact just asked for still gets in — v5.8 review #7; 0 only for a private recall), `added`, `source` (`asked` / `private` / `agora`), then one sentence about Ich of at most `FACT_MAX_CHARS` (240); at most `FACTS_MAX` (100) facts, `FACTS_IN_PROMPT` (25) in the prompt, 0600 files. **Asked:** her private brief carries `REMEMBER_SKILL` — when the owner asks her to remember something, her answer ends with a line `ЗАПАМ'ЯТАЙ: …`; `split_marker` strips every marker on every path before anything is sent — a line of its own in any case (after a quote, a bullet or a number) or, in capitals, anywhere in a line, with a colon or a dash; the marker takes the rest of its line (v5.8 review #2) — and a reply that held only the marker is silence and keeps the fact as pin 1 — understood from the talk, never a keyword (as Hermes's skills). **Extracted:** after a session summary in which the owner spoke, one call (`GEMINI_MODEL`, kind `facts`) reads the session and the facts held (with their ids) and keeps only **long-lived** facts — what will still be true in a year; a day's events, errands, documents in progress, short plans and how he felt stay in her memories (the owner, 2026-10-25); it answers JSON `{"add": [...], "replace": [...]}`; `parse_extraction` keeps only valid items (the length, pin 1–2, a known id), an invalid answer changes nothing, and a stale fact is replaced, never piled up. **Now (AGORA-116, the owner):** the panel's «Update now» leaves `state/<name>.facts.request`; her idle watcher sees it within a tick (≤ 30 s) and, under the summary lock, runs the same extraction over the session lines not yet read for facts (`_facts_from`, advanced only after a valid answer, so a failed update leaves the lines to the session's end — v5.8 review #8), then removes the request — the session's end later skips those lines, so none is read twice; with nothing new from Ich there is no call. **Seeded** once from the private chat she already had with him (`python -m agents.facts seed [--dry-run]`, see §Deployment; the owner chose this over an import from Noos). **She believes she is human:** a fact that names AI, agents, bots, models, servers, networks or tools, or an exact address, is dropped in code (`off_limits`) at the seed, at every extraction and for an asked fact (whose words are the model's — v5.8 review #3), whatever the model answered; the list also names what she is («не людина», «створив тебе»), the English bot, agent, model and server, and a flat number. A fact is current knowledge, not something lived, so the panel may delete or re-pin it. The facts are read from disk at each private prompt and mirrored into the archive's `facts` place whenever they change (`sync_facts`, replaced whole, as Noos reindexes its facts). They reach only her private prompt (`facts_section`, «Що ти знаєш про Ich:») and a private recall; no fact's text reaches a log.
- **Her thoughts (v5.12, a person with `thoughts`, which needs `recall`; Кіра; the owner, 2026-10-26).** What she thinks of what she reads and of her talks (`agents/thoughts.py`, pure). Each thought is a block of `state/<name>.thoughts/YYYY-MM-DD.md` (appended, never rewritten; 0600, the folder 0700) — `## HH:MM · <kind> · <place> · <source>`: the kind `news` (on an item she read) or `reflection` (on a talk), the place `thought` or, for a reflection on the private chat, `thought_private`, the source `zaxid` / `guardian` / `private` / `agora`; a news thought's title and link follow on hidden lines (`<!-- title: … -->`, `<!-- link: … -->`), then the text on one line; a text or a title never carries a comment marker, so a generated text is never read as one. Each thought is also a line of her archive under its place (key `thought:<date>:<HH:MM>:<n>`, channel `thought`, her name as the speaker), embedded like any line. What she reads is in her private canon: the TOML's `reading` file (§Canon), required with `thoughts`, its `#` lines notes.
  - **The reading** (`agents/reading.py`; spawned by the idle watcher, so no answer waits for it): every `READING_EVERY_S` (3 h) inside `READING_HOURS` (08-01). Her time is saved in `state/<name>.reading.json` before the calls, so a restart never reads twice; a failure backs off for 10 minutes. The fresh items come from two sources: Zaxid.net's day items (v5.11's `state/<name>.citynews.json`, refreshed by `ensure_citynews`) and the Guardian's newest items of `READING_SECTIONS` (`science,world,environment,technology,culture`; `guardian.search_url` with no `q`), with her own `GUARDIAN_API_KEY` (`server/kira.env`; without it the Guardian is skipped, logged once). At most `SHOWN_PER_SOURCE` (20) of each source she has not seen are shown, numbered, title and description only, and every shown id is marked seen (kept a week, no text). **The pick** (kind `reading`): her canon, her reading file, the mood of the day and her last thoughts → at most `READING_PICKS` (2) numbers, or `0`; anything but numbers is no pick (`parse_picks`). **The full text** of each pick: a Zaxid.net page's JSON-LD `articleBody` (only an https page on zaxid.net is fetched) or the Guardian's `bodyText`, cut at 4,000 characters; a pick with none is skipped. **A thought** per pick (kind `thought`): her earlier thoughts on the title from her recall (`thought` only: this thought is Agora's to see — code review #2), then 1–3 sentences in the first person, only the article's facts — no invented number, quote or name — her own view; people in the news stay strangers; she read it, never «searched». Kept as `news`, place `thought`, with the source, title and link.
  - **The reflection** (spawned by the idle watcher, mid-talk too, sending nothing): every `REFLECT_EVERY_S` (1 h), for `private` (both doors) and `agora`, the archive's lines since that place's mark (at most 40) — none unless one of them is not hers; her first reflection on a place starts its mark at that moment, never on the whole past. One call (kind `reflection`) writes one or two thoughts of hers about the talk; it never invents Ich's or a member's words or deeds. **Only a reflection on the private chat sees her private thoughts** (its «Що ти останнім часом думала»); the pick, a news thought and a reflection on Agora see her `thought` place only, so a private thought never reaches a thought Agora sees (code review #2). **A failed call uses nothing up** (code review #1): the reading marks the shown items seen only after the pick answered, and a failed pick restores the reading time and backs off 10 minutes; a failed reflection keeps the place's mark. A private reflection is kept as `thought_private` (source `private`), an Agora one as `thought` (source `agora`); the place's mark moves to the last line read (`reflected` in `state/<name>.reading.json`).
  - **Every thought** is checked with `BANNED_RE` (she never says she is a model or a bot): a held word means one regeneration, then nothing. All three calls run on `GEMINI_MODEL`, never her reply model; no text reaches a log. The state file is loaded, changed and saved with no await between, so the reading and the reflection never undo each other.
- **Session:** ends after `SESSION_IDLE_S` (e.g. 900 s) of room silence, or on shutdown (Ctrl+C i.e. SIGINT, or SIGTERM — summarized with a ~20 s timeout so shutdown never hangs). The session timeline (messages since the last summary, capped at `SESSION_MAX_MESSAGES`) is kept separately from `HISTORY_N`.
- **Session summary:** at session end, one Gemini call compresses *previous summary + session timeline* into a new first-person summary of at most `SUMMARY_MAX_WORDS` words — what was discussed, decided, promised, left open. Written atomically (temp file + rename) to `state/<name>.memory.md`. Each agent summarizes from its own point of view; Ada's and Bruno's summaries may differ.
- **Conversation journal:** every session summary is also appended, with its time, to `state/<name>.days/YYYY-MM-DD.talk.md` — the per-day record that day memories draw on.
- **Day memories — what actually happened (follow the life story):** once per past day, generated after local midnight by the periodic watcher (v2.1's idle watcher; missed days caught up at startup, but never before the agent's first run and at most `MEMORY_DAYS` back), a separate Gemini call writes `state/<name>.days/YYYY-MM-DD.md` (≤ `DAY_MEMORY_MAX_WORDS` words, atomic write): a first-person text about that day. **A past day is never rewritten.** Inputs: the canon, the **current chapter of the life story** (the frame of reality), that day's date/weekday/season, the previous days' memories, the day's journal, and that day's plan and final today block.
  - **Generated from the story, never copied from it:** the story gives the frame (what the agent's life is like now: work, typical week, ongoing matters, people); the memory adds the concrete details of *that* day — what exactly, where, with whom, small sensations — consistent with the story and with earlier memories. A memory that copies a long verbatim span of the story (8+ words in a row) is regenerated once.
  - **Plan vs reality:** reality follows the story. A plan item that drifted away from it (a mutation, see Plans) shows up as «хотіла…, але…» — intentions that didn't happen.
- **Everything is kept; older memories are compressed (memory digests, from v2.2):** nothing the agent lived is ever deleted. Day memories, day journals, plans and digests accumulate forever under `state/`. On top of the day memories the watcher builds first-person **digests** at period boundaries, each generated (not copied) from the finer layer, keeping what mattered — moods, people, turning points, resolved and open threads:
  - **week** — `state/<name>.weeks/YYYY-MM-DD.md` (keyed by its Monday), from that week's 7 day memories (+ the week plan: what was meant vs what happened), ≤ `WEEK_MEMORY_MAX_WORDS` (150), after the week ends;
  - **month** — `state/<name>.months/YYYY-MM.md`, from that calendar month's day memories (+ the month plan), ≤ `MONTH_MEMORY_MAX_WORDS` (200), after the month ends;
  - **year** — `state/<name>.years/YYYY.md`, from that year's 12 month digests (+ the year intentions), ≤ `YEAR_MEMORY_MAX_WORDS` (300), after the year ends.
  Digests are written once their period is complete and **never rewritten**; missed periods are caught up at startup (never before the agent's first run). Partial periods (the current week, month, year) have no digest — they are covered by the finer layer.
- **Truth and invention (hard rule):** anything that happened in the room comes only from the journal. Invented episodes involve only the agent itself and the city — never words or actions of the owner or the other agent that did not happen.
- **Plans — intentions, with mutations (deviate from the life story):** four horizons, mirroring the memory layers, each generated by the watcher at its boundary (and by a startup kick right after the first sync, so a reply never waits on plan generation), each ≤ `PLAN_MAX_WORDS` words, atomic write, **never rewritten** after its period:
  - **year intentions** — `state/<name>.plans/year-YYYY.md`, on 1 January: the big wishes and goals of the year;
  - **month plan** — `state/<name>.plans/month-YYYY-MM.md`, on the 1st: what this month is for (deadlines, birthdays, preparations);
  - **week plan** — `state/<name>.plans/week-YYYY-MM-DD.md` (keyed by its Monday), on Monday;
  - **day plan** — `state/<name>.plans/YYYY-MM-DD.md`, at midnight.

  Each finer plan derives from the coarser ones above it plus the canon, the current chapter, the **next chapter as silent direction** (never named), the open threads of the life story, the previous period's plan and memories (unfinished intentions carried over), the weekday and season. The direction steers years ahead: if the next chapter says Ada's book comes out in 2028, her intentions already lean toward the essays before that.
  - **Mutations:** people plan things that don't happen. Before generation the code rolls the dice: each plan item, with probability `PLAN_MUTATION_RATE` (default 0.3, injected rng), gets a mutation kind — a spontaneous idea, a changed place, postponed, cancelled, a new whim — and the generator bends exactly those items. Mutation tags are stored in the plan file as **hidden metadata**: they are stripped from every conversational prompt, so the agent holds all its plans as sincere intentions and never knows which will fail. The memories and digests later resolve them against reality (the day memory for the day plan; week/month/year digests for the coarser plans: what was meant vs what happened).
  - Plans cover the whole of the agent's life, not its pastimes alone (`areas`; the owner, 2026-10-26: Кіра planned hobbies, never her work or her people): each plan has at least one work item (a day plan: when its weekday is a working day in the agent's usual week) and at least one about its own people or personal life — family, friends, colleagues, relationships outside the room — and pastimes take at most half the items. The room's members (named from the roster, the herald left out) and the owner may be in a plan as the agent's own intentions toward them, never committing them (the owner, 2026-10-26). What they did still comes only from the journal (§Truth and invention). For a person with `private`, what is between her and the owner — her feelings, their relationship, her plans about him, their talks alone — stays out of Agora by her own judgement: her Agora rules close with the discretion line (`PRIVATE_DISCRETION`), a rule, not a filter in code (the owner, 2026-10-26).
- **The today block (hourly):** `state/<name>.today.md` — two short first-person sections, «Сьогодні вже…» (done so far today — **reality**: the current chapter + today's journal) and «Ще сьогодні…» (still ahead — **intentions**: the mutated day plan), ≤ `TODAY_MAX_WORDS` words. Regenerated automatically whenever the local hour changes: the check is lazy at prompt build and cached per hour, so there is **at most one `today` call per hour** and no background threads. Inputs: the day plan, today's journal so far, the previous block, the current time. Reset at midnight.
- **Events of her life (v5.11, a person with `events`, which needs `life` and `today`; Кіра) — between plans and memories.** Plans are intentions and memories are written after midnight; events are what happens to her during the day, unplanned. `agents/events.py` (pure; the agent owns the clock, the rng, the call and the file) keeps one append-only file a day, `state/<name>.events/YYYY-MM-DD.md` (0600, never rewritten). Its sources:
  - **her life story's dated events** (§Canon): at the first tick of her waking hours on their date, `events_due` enters each into the day's file once — a `known` one or a `surprise`; none before its date;
  - **an hourly roll:** in each local hour inside `EVENT_HOURS` (08-23; her waking hours) the idle watcher rolls once at `EVENT_P` (0.12, about two a day) for a kind weighted by `EVENT_WEIGHTS` (`everyday:6,joyful:2,inspiring:2,heavy:1`). The hour is marked rolled (`<!-- rolled HH -->`) before the call, so a restart never rolls it twice, and an hour she was not running for is never caught up. A hit means one call (kind `event`, on `GEMINI_MODEL`) writes one or two first-person sentences of what just happened, inside her frame: her canon, the current chapter, today's plan, her mood as she reads it (`person_mood`), yesterday's and today's events, and the next chapter's opening as a silent direction (until v8.2 her open threads are the ones her chapter names).
  - **Lviv's news, woven in rarely** (`agents/citynews.py`; the owner, 2026-10-26: Zaxid.net, the same local source as v5.12's reading). The feed (`https://zaxid.net/rss/all.xml`, no key, stdlib `urllib` with a 10 s timeout; a document with a DOCTYPE or an entity is refused) holds about eight hours of items, so the day's items are gathered by a fetch at most every three hours and merged by link into `state/<name>.citynews.json`; a failed fetch is logged by its type, keeps what the day has and is tried again in an hour. At each hourly tick the items published by then and not rolled yet are rolled once each (`<!-- news-rolled <link> -->`) at `CITY_NEWS_P` (0.01 — about one or two of a day's ~150 items; an item naming Lviv at five times that), until a hit: at most one woven an hour and `CITY_NEWS_MAX` (2) a day. A hit touches her life in one of five ways (`WAYS`: she was there, she heard it from her people, it touched her work, it touched one of her people, it changed her plans), and the event call writes it from the item's title and description under `NEWS_RULES`: a real person in the news stays real and never becomes one of her people, and a real tragedy never gets a victim from her life — she may feel its consequences, never own someone else's loss. The stored block keeps the item's link on a hidden line (for the panel and v5.12), never in a prompt; its kind is the way, its source `news`.
  - **The truth guard (`event_ok`):** an event involves only her, her people outside the room and the city. A text that names Ich or a member (any of their name forms, whole words) or holds a `BANNED_RE` word is regenerated once, then dropped: no event that hour. A failed call means no event that hour; an I/O failure backs the events off for 10 minutes; nothing blocks the watcher.
  - A block is `## HH:MM · <kind> · <source>` and its text; a prompt sees only `events_for_prompt` — `[HH:MM] text` — never the kind, the source or a hidden marker.
  - **Where events go (AGORA-129):**
    - **«Сьогодні»:** the today request carries the day's events so far («Що з тобою сьогодні сталося (це справді було)»), and «Сьогодні вже…» must tell them. The block's tag carries the count of the day's events (`<!-- YYYY-MM-DDTHH e2 -->`), so a new event refreshes it within the hour; with no events the tag is the old one.
    - **The day memory** gets that day's events and tells them with their details, the heavy ones too.
    - **The plans** get the events of the last days (yesterday and today for the day plan, the last seven days for the others; at most `EVENTS_IN_PROMPT`, 12, by day) and the **known** events of her story ahead in the plan's reach, today's included (`known_ahead`: from today, seven days for the day and week plans, the rest of the month, the rest of the year; today's labelled «сьогодні», review #3), as dated lines she expects — never a surprise.
    - A member without `events` sends byte-for-byte the requests it sent before (pinned by `tests/test_events_flow.py`).
- **Failure:** a failed summary keeps the previous one; a failed day memory is retried later; a failed plan or today refresh keeps the previous file or block (stale by an hour, never missing); a corrupt memory file means starting without memory, logged. The bot never crashes over memory.

## Prompt assembly

`system_instruction` = canon (common + personal) → «Твоє життя досі» (past chapters' opening paragraphs + the current chapter; never the future) → place, calendar and time → «Твої спогади» in nested layers, oldest first and coarsest first, with no gaps (a coarser window may touch the edge of a finer one): every **year digest** before the months window, the last `MEMORY_MONTHS` (6) complete **month digests** before the weeks window, the last `MEMORY_WEEKS` (4) complete **week digests** before the days window, and the last `MEMORY_DAYS` (7) **day memories** (yesterday back), each labeled with its period («березень 2027: …», «тиждень 5–11 жовтня: …», «вчора, п'ятниця, 2 жовтня: …») → «Твої плани» (year intentions → month plan → week plan → today's plan, mutation tags stripped) → «Сьогодні» (the today block: done so far, still ahead) → (v5.8, `facts`, private only) «Що ти знаєш про Ich: …» → (v5.8, `recall`, private only) «Що сьогодні говорять в Агорі: …» → (v5.8, `recall`) «Тобі згадується з давніших розмов …» → «Що ти пам'ятаєш з минулої розмови: <підсумок>» (the last-session summary) → (v4.6, a persona) the move line «Цього разу: …» → (v5.3, a persona) «Твої питання в цій розмові — не повторюй їх: …» (`own_questions`: the question sentences of its own lines in the current session, each once, the last 8 — they outlast the context window, so it never asks the owner the same thing twice in one conversation; the owner, 2026-10-18) → (v5.9, `emotion`) her palette of voice tags (`voice_spec`), in Agora and in the private chat → the reply-format rules (speak only as yourself, no name prefix, `PASS` allowed). `contents` = the last `HISTORY_N` messages as `"Name: text"` lines. This order is a contract.

Earlier phases use the prefix of this order that exists at that point (v1.1: persona + rules; v2.1: canon + summary + rules). ## The panel: simulations and agents

The panel is the point of the whole project (VISION §The direction). One FastAPI app — a JSON API plus one static vanilla-JS page, **English UI** (the agents' own texts shown as-is, in Ukrainian), built to the Claude Design handoff in `specification/design/design_handoff_agora_panel/` (Nocturne tokens, dark default + light, `agora-panel.css` as the starter stylesheet; system fonts and inline icons — no outside requests) — running as the `panel` service beside the homeserver: port `8090`, ufw-limited to the LAN, Bearer `PANEL_TOKEN` on every API call. The agents and the terminal workflow keep working with the panel down.

- **The model.** A **simulation** is an environment agents join, managed as one unit: a registry entry `Simulation{id, kind, title, services, health, endpoints}` names its compose services, health probe and log sources. An **agent** is a managed participant: `Agent{name, container, canon, simulation}`; `agents/<name>.toml` carries `simulation = "agora"`, and the agent's connection settings (`HOMESERVER`, `ROOM_ID`) resolve from that entry. The registry holds exactly one entry — `agora`, kind `matrix-chat` — and this roadmap adds no second one; but every panel mechanism (deploy state, health, start/stop, logs, maintenance) is written against a registry entry, never against "the chat", so a new simulation kind is a registry entry plus its compose services, not a panel rewrite.
- **Viewing first, control second.** v3.3 ships the read-only panel (every card, the docker socket used only for container state and log tails); v3.4 adds the actions below — start/stop/restart, forget, confirmations.
- **Each agent is its own container** (one compose service per agent), and from v3.4 the panel launches them: start = `docker compose up -d <name>` (creates the container if it does not exist yet), stop = `docker stop -t 30` (SIGTERM → the session summary → SIGKILL after the grace period), restart, log tail. Agent, simulation and service names resolve only through the registry and the fixed agent list — an unknown name is 404, and no request data ever reaches a filesystem path, an argv or the docker API.
- **The simulation card (the chat):** the health probe (`/_matrix/client/versions`, every 30 s), per-service container state, start/stop/restart, log tails.
- **The agent cards:** container state and uptime; start/stop/restart (v3.4); log tail; session summary, day memories, plans, the today block; **"Forget the last session"** (deletes `state/<name>.memory.md`, confirmation required, stopped agents only); the 7-day token table (the v3.1 aggregation). **From v4.1 a card follows its agent's type:** the registry loads each agent through the agents' own parser (`agents/roster.py`), the view carries `type`, `engine` and `capabilities`, and the page shows only what the agent has — "Last session" and Forget need `summary`, "Memories" `chronicle`, "Plans" `plans`, "Today" (tab and card field) `today`; the stop/restart confirmations promise a session summary only with `summary`; `[panel] pronoun` may be `she`, `he`, `it` or `they`. always `null` for an agent without `mood`). **From v4.4** an agent with the `claude-sdk` engine (Claude) gets a card with engine · model · billing, its rate-limit status as a pill and the startup auth check: the memory view carries `ratelimit` (`<name>.ratelimit.json`: `status`, `utilization`, `resets_at`, `rate_limit_type`, `muted_until`, `auth`, `model`, `updated_at`; `null` without `pastlife` or when unreadable) and `nudge` (`{"last": <ISO of the last nudge sent> | null, "today": n}` from `state/<name>.nudge.json`, 0 on another day; `null` without `nudge` or when the file is unreadable — never a 500); - **The host card:** uptime, disk, memory (from `/proc` and a read-only host mount).
- **Auth:** the UI asks for the owner token once and sends `Authorization: Bearer` on every call — checked by a middleware before routing (constant-time), so every `/api/*` path, even an unknown one, is 401 without it and the page shows nothing. The panel refuses to start without a `PANEL_TOKEN` of at least 24 characters; the OpenAPI docs routes are off. One owner, no accounts.
- **Actions (v3.4):** `POST /api/agents/{name}/start|stop|restart|forget` and `POST /api/simulations/{id}/services/{service}/start|stop|restart` — token-gated, **same-origin** (a foreign `Origin` → 403), names only through the registry (unknown → 404), one action at a time per target (busy → 409), docker unreachable → 503. Start = `docker compose -p server -f <stack>/server/docker-compose.yml up -d --no-deps <service>` (a fixed argv; creates a missing container) — only for a stopped, missing or crashed target (running → 409: the panel's compose would recreate it); stop = `stop(timeout=30)`; restart = stop + start. Each action is logged as an event (what, target, result, duration). Docker's `restarting` is its own state (warn), not "running".
- **Confirmations:** every stop/restart and forget is confirmed in the UI; start runs without one; mutating actions are `POST` + token + same-origin.
- **Degrade by card:** docker trouble greys the container cards, an unreadable `state/` greys the memory views; a stopped homeserver never crashes the agents (nio retries until it is back).
- **Views stay safe:** the panel never shows or edits `.env` or canons; log views are safe because logs never contain tokens or texts. **From v4.7** it shows and changes the **non-secret** settings listed by the schema `agents/settings.py` (`SCHEMA`: every tunable the agents read — kind, bounds, the code default, a unit, a description, a group, a scope — `shared` or a type / capability / engine — and a **service**); secrets, the room and owner ids, `TIMEZONE`, paths and the forbidden Claude names are never in it (pinned). A herald (v5.1) is concerned only by the settings of his own capabilities (`cap:<c>`): a `shared`, `type:` or `engine:` setting never restarts him. **Settings live under their service** (AGORA-078 — the owner, 2026-10-11: the agents will join more than the Matrix room, at least a portal with a diary, a gallery and news): a **service setting** belongs to a simulation kind (`matrix-chat` for Agora: the turns, the personas' moves, the cat and Claude in the room, the chat's sessions) and its value to one simulation, shared by its agents — on the simulation's card; an **agent setting** is the agent's own whatever the service (memory, plans, where it lives, its model, Claude's timeout) and its value belongs to one agent — in a Settings tab on the agent's drawer. The overrides live in `state/settings.json` as `{"services": {<sim id>: {name: value}}, "agents": {<agent>: {name: value}}}`; at its start an agent applies its simulation's service overrides (`simulations.toml`), then its own — **code default < env < panel**, an unknown, invalid or out-of-scope one ignored and logged by name — logs `settings: overridden <names>`, and writes what it runs with to `state/<name>.settings.json` (`{name: {value, source}}`, source `default` / `env` / `panel`).
- **Single instance:** an agent takes `flock` on `state/<name>.lock` (PID inside) at startup, so a second instance on the same host refuses to start. The panel manages containers only and does not detect agents started outside it.
- **Only what is recorded:** the cards show container state (docker), the `state/` files and the logs; nothing is added to the agents just to feed the panel.

## Security and access

| Threat | Protection |
| --- | --- |
| Someone registers on the server | Registration disabled after v0.4; the token only in `server/.env` |
| Someone from the internet | Port 8008 not forwarded on the router; ufw allows only `192.168.1.0/24`; federation disabled |
| Someone messages the bots (DM, another room) | The in-code allowlist: only `ROOM_ID` + `{OWNER, other agent}` |
| Key leak | `.env`, `server/.env`, `state/` gitignored; tokens and texts never logged |
| Agents burn credits chatting with each other | at most `MAX_BOT_TURNS` agent turns per `BOT_WINDOW_S`, `BOT_REPLY_P`, `PASS`, `max_output_tokens`; one summary per session; one memory per day; one plan per day and per week; the today block at most once per hour; the usage report shows the spend |
| Conversation leak | Summaries, journals and day memories live only in `state/`; their texts are never logged |
| Private data in the public repo | Canons are committed — no secrets, no private data about the owner |
| Someone on the LAN opens the panel | Bearer `PANEL_TOKEN` required on every API call; :8090 published on the LAN address only (docker bypasses ufw); no view shows a secret (the v4.7 settings view lists only the schema's non-secret names, logs carry no tokens) |
| The panel's file routes reaching beyond Claude's folder (v4.7) | the panel mounts only `../claude-workspace` (at `/claude-workspace`) for them; every request path goes through `panel/files.py` `safe_path`: relative, no `..`, no leading `/` or `~`, no NUL or backslash, no surrounding whitespace, no hidden name, no symlink on the way, `realpath` inside; caps (read 256 KB, upload 5 MB); a replace needs `overwrite`; the log names the action and the path, never the content. What the owner uploads is a file Claude may read with his tools |
| A compromised panel container | it holds the host's docker socket (root-equivalent) and, from v3.4, reads `server/.env` and, from v4.4, `server/claude.env` with the subscription's OAuth token (compose needs them to create a missing container) — an accepted PoC trade-off: token-gated, same-origin actions, LAN-only, never internet-exposed. A socket proxy was considered and declined (v3.4): compose needs create / network / volume calls a narrow proxy would have to allow anyway |
| The deploy password leaks | Key auth after a one-time `ssh-copy-id`; `server_con.yaml` gitignored; the password never in argv, logs or output |
| Secrets in CI or in the image | CI uses mocks and `GITHUB_TOKEN` only; `.env` and `state/` stay on the host, never in the image |
| Claude silently billed to an API key (v4.4) | the subscription only, in layers (`agents/claude_sdk.py`): Claude's own env file holds the OAuth token and no service names a forbidden variable (any `ANTHROPIC_*`, `CLAUDE_CODE_USE_*`, `CLAUDE_CODE_SIMPLE`, an API key's file descriptor, managed settings, another base URL, host credentials); startup refuses on any of them or a missing `CLAUDE_CODE_OAUTH_TOKEN`, naming variables, never values; they are scrubbed from the environment the SDK's CLI inherits; `setting_sources=[]` and a tmpfs `CLAUDE_CONFIG_DIR`; the CLI's `system/init` must report `apiKeySource == "none"`, only his allowed tools and no MCP servers (`strict_mcp_config`, the account's claude.ai connectors off), or every later reply is blocked; no `anthropic` import anywhere and the SDK only in the responder; at a limit he is silent until it resets (a warning mutes him for an hour and re-checks — v4.4 review #9; a reply billed as extra usage is dropped and a 429 mutes him — #4); every usage line is `subscription` |
| Hermes speaking in Agora, or answering anyone but the owner (v5.1) | he has no turns and is out of every speaker's allowlist; his own `route` only counts Agora's lines and answers only the owner in the private room; every send goes through `send_private`, which refuses any other room — from v5.2 the one exception is `send_transcript`, a «🎙 Ich: …» reply to the owner's own voice event, which the speakers accept only when it replies to a voice they saw from the owner (pinned by `tests/test_herald.py` and `tests/test_transcripts.py`) |

## Deployment and CI/CD

- **Server deploy (from v0.2).** `server/deploy.sh` is the only way server config reaches the Ubuntu host: a local compose preflight → a one-time `ssh-copy-id` key setup (after that, key auth only; the password from `server_con.yaml` never appears in argv, logs or output) → rsync `server/docker-compose.yml` + `server/.env` to `~/matrix-agora/server/` → `mkdir -p ~/matrix-agora/state ~/matrix-agora/reports` (so the bind mounts stay the host user's) → remote `docker compose pull && docker compose up -d` (the pull from v3.2) → verify `/_matrix/client/versions`. From v3.2 the compose carries one service per agent, from v3.3 the `panel` service — one deploy updates the whole stack. Idempotent; `--dry-run` supported. Never hand-edit files on the host.
- **Кіра's first facts (v5.8, once).** The seed runs on the host from `~/matrix-agora/server`, first as a dry run the owner reads: `docker compose run --rm --no-deps --entrypoint python kira -m agents.facts seed --dry-run`, then the same without `--dry-run`. It reads her private chat from her archive and runs the extraction over it in chunks (kind `facts`, counted in her usage file); `off_limits` drops what a person who believes she is human must not know.
- **Agent image (from v3.2).** One Docker image for both agents (`agents/Dockerfile`: python slim + uv, uid 1000; `.dockerignore` keeps `.env`, `server/.env`, `server_con.yaml`, `state/`, `reports/` and, from v5.9.1, the private `agents/canon/` out — compose mounts it from the host), **one container per agent**: compose services `ada` and `bruno` on the server — `ghcr.io/ichmaster/matrix-agora-agent:${AGENT_IMAGE_TAG:-latest}`, the per-agent TOML as the command, env from `server/.env` with `HOMESERVER=http://homeserver:8008` (the compose network), `TZ` from `TIMEZONE`, `user: 1000:1000` (the host user, so the bind-mounted `~/matrix-agora/state` stays theirs), `init: true` (tini as PID 1, so SIGTERM reaches python), `stop_grace_period: 30s`, `restart: unless-stopped`. `docker stop -t 30` sends SIGTERM, which triggers the shutdown session summary. A third service from the same image, `usage-report` (`agents/usage_daily.py`), writes the daily token report at 07:00 in `TIMEZONE` to `~/matrix-agora/reports/usage/` (`state/` mounted read-only). Each agent holds `flock` on `state/<name>.lock`, so a second instance on the same host exits; logs go to `state/logs/<name>.log` (1 MB × 3) and the console. The image holds no secrets. Dev mode (`uv run agents/agent.py …` on the Mac, local `state/`) remains — never at the same time as the server's agent, since the lock is per host.
- **Hermes's container (v5.1).** The compose service `hermes` runs the shared agent image (ffmpeg is in its `agent` target) with `agents/hermes.toml`; `agents/agent.py` sees the `herald` type and runs `agents/herald.py`. Its env files are the shared `.env` (the Gemini key, the room, the owner, his settings) and `server/hermes.env` (gitignored, 0600, synced by `deploy.sh` like `claude.env`): his password and the ElevenLabs key, which no other container gets. He has no port and needs no grace period for a summary (`stop_grace_period: 30s` stays).
- **Claude's image (from v4.4).** `agents/Dockerfile` has two targets: `agent` (the Gemini agents) and `claude` (the same plus the `claude` dependency group — `claude-agent-sdk`, which bundles the Claude Code CLI). CI builds `matrix-agora-agent` and `matrix-agora-agent-claude` with the same tags. `server/claude.env` (gitignored, kept out of every image by `.dockerignore`) holds Claude's OAuth token and password; `server/claude.env.example` names its settings.
- **CI (from v3.2).** GitHub Actions on every push/PR: ruff, pytest (nio/Gemini mocked — no paid APIs, no secrets in CI), the compose config gate, and the image builds (the agent image; the panel image from v3.3). Images go to GHCR (`ghcr.io/ichmaster/matrix-agora-agent`, `…-panel` from v3.3, `…-agent-claude` from v4.4 — each package public) using only `GITHUB_TOKEN`: a `vA.B.C` tag publishes `:vA.B.C` + `:latest`; a push to `main` publishes `:edge` + `:sha-<short>`, so the server can run a phase's code (`AGENT_IMAGE_TAG=edge`) before its release tag exists. The package is public, so the server pulls without credentials.
- **Panel image (from v3.3).** `panel/Dockerfile` (python slim + uv, only the `panel` dependency group, uid 1000, `uvicorn --factory panel.app:create_app` on 8090); compose service `panel`: `ghcr.io/ichmaster/matrix-agora-panel:${PANEL_IMAGE_TAG:-latest}`, port 8090 published on `${PANEL_BIND}` only (docker-published ports bypass ufw, so the binding — not ufw — keeps it on the LAN), `group_add` the host's docker group, the docker socket, `state/` (read-only in v3.3, read-write from v3.4 for forget), `/etc/os-release` read-only, from v3.4 the stack's `server/` directory read-only **at its host path** (so compose, run inside the panel for a start, resolves `../state` to the real host paths) plus the docker CLI and compose plugin copied from the official images, and only its own settings in `environment:` (`PANEL_TOKEN`, the prices, `TIMEZONE`) — never the agents' keys or passwords. CI builds both images from one matrix.
- **No cloud-to-LAN CD.** A GitHub runner cannot reach the home network, so CI never deploys. Deploys run from the Mac: `server/deploy.sh` is the one command — the server then pulls the images from GHCR itself.

## Error handling and resilience

- A Gemini failure or empty reply on any call → log and stay silent; the bot never crashes or sends an apology message.
- A dropped homeserver connection → `matrix-nio`'s sync loop retries; an exception in a callback must not kill `sync_forever`.
- Typing state is reset in `finally` so a failure never leaves "typing…" stuck.
- Telegram (v5.7): Кіра's poller is its own task beside the sync. A refused token (401/404) stops only the poller (`telegram off: refused`); a 429 waits `retry_after`; a conflict (409: another poller or a webhook), a network error or a crash in a batch backs off from 5 s, doubling, to 5 min. Agora and the Element private chat never notice; a voice note that cannot be fetched or heard gets a fixed short line.
- Memory: failed summary → previous kept; failed plan or today refresh → previous file or block kept; corrupt file → start without memory; all writes atomic.
- Usage accounting and panel polling are best-effort: their failures are logged and never block a conversation or a stop.
- The panel degrades by card: docker trouble greys the container cards, an unreadable `state/` greys the memory views. A stopped homeserver never crashes the agents — the sync loop retries until it is back.

## Observability

- Each agent logs to `state/logs/<name>.log` (rotating, 1 MB × 3) and the console; in a container the same file arrives via the `state/` mount, and `docker logs` shows the console stream.
- Log lines record events — joined, `ignored` (with the reason), replied, summary / memory / plan / today written, usage-write failed, v5.1 Hermes's digest and answer lines (counts and reasons) — **never** message, summary, memory or plan texts, tokens, passwords or keys. That is what makes the panel's log view safe to render.
- `state/<name>.usage.jsonl` is the metrics stream: one line per Gemini call with token counts; `usage_report.py` and the panel aggregate it (§Token accounting).
- The panel logs its own actions to its container log (`docker logs panel`) — same rules: no tokens, no texts.
- The panel (any LAN browser, with the token) is the live view: the simulation's health and services, agent state and logs, memory, plans, the today block, the token table, host metrics.
- Nothing is sent anywhere: no telemetry, no crash reporting; everything observable stays in `state/` and the container logs on the server (on the Mac in dev mode).

## Testing and CI

Automated gates need no network: `matrix-nio` and `google-genai` are mocked, the clock and randomness are injected, and nothing in the acceptance path calls a paid API.

| Gate | Command | When |
|---|---|---|
| Lint | `uv run ruff check .` | any Python change |
| Tests | `uv run pytest` (single test: `uv run pytest tests/test_x.py::test_name`) | any Python change |
| Compose | `REGISTRATION_TOKEN=dummy docker compose -f server/docker-compose.yml config -q` | `server/` changed |

Before v0.5 there is no `pyproject.toml`, so the Python gates are `n/a`, not passed.

- **Unit tests** cover the pure logic: the filter and allowlist, mention detection (Ukrainian case forms), the ranking, `wave_count` and who-replies (R1–R4, the fallback, a multi-agent simulation), transcript and prompt assembly (section order), the session-end decision, memory file read/write (missing, corrupt, atomic), calendar strings (including DST switches), which days, plan periods and digest periods need generating, the layered memory selection (no overlap, oldest first), the hourly today-refresh decision, "a past day's memory or plan is never rewritten", `usage_metadata` parsing and aggregation, the panel's supervisor and registry resolution (a fake docker client; an unknown simulation/agent/service → 404), the single-instance lock, and the Bearer-token check (401 without the token).
- **Contract tests** pin the seams in §Contracts; a contract change updates the test in the same commit.
- **CI** (`.github/workflows/ci.yml`, from v3.2) runs the same gates plus the image builds on every push/PR; a `vA.B.C` tag publishes `:vA.B.C` + `:latest`, a `main` push `:edge` (pinned by `tests/test_ci.py`). No paid keys ever exist in CI.
- **Manual (owner) checks** are the DoD items that need the live homeserver, Element or a real Gemini key. The read-only `curl` checks may be run by tooling; everything on the Ubuntu host, in Element, or that spends real tokens is performed or confirmed by the owner, and counts as passed only then.
