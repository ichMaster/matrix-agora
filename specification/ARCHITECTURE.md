# Architecture — matrix-agora

## Overview

Two small axes bound by one agent codebase. **The agents' capabilities** grow: echo → Gemini replies → turn-taking → canon + session memory → world awareness (place, clock, day memories, plans, the hourly today block) → token accounting. **The operations surface** grows separately: terminal processes on the Mac first, then Docker images with CI behind them and deployment to the Ubuntu server, and finally the **panel** — the point of the whole project — served from that server. The panel manages **simulations** (environments agents join; the chat — the homeserver and the room — is the first and only one here) and the agents connected to them. Everything the agents do rides on the plain Matrix client-server API.

## Components

- **Homeserver:** [Continuwuity](https://continuwuity.org) — a Matrix homeserver in Rust: one Docker container, embedded RocksDB, no Postgres. `server_name = agora.lan` is only the domain part of user ids (`@ada:agora.lan`); clients connect to `http://192.168.1.197:8008` directly, so no DNS is needed. Federation and encryption are disabled; registration is open (token-gated) only during setup, then closed. The compose file is the deliverable of ROADMAP v0.1.
- **Client:** Element Desktop on the Mac. Specifically Desktop, not app.element.io — the web version runs over HTTPS and will not connect to an HTTP homeserver on the LAN (mixed content).
- **Agents:** the same `agents/agent.py` with different TOML configs (account, canon, simulation). Libraries: `matrix-nio` + `google-genai` (async `client.aio.models.generate_content`, model `gemini-2.5-flash`). **Each agent is its own Docker container** — one compose service per agent — on the Ubuntu server from v3.2; `uv run` on the Mac remains the dev mode. The names "Ada" and "Bruno" are placeholders. From v4.1 a reply goes through the **responder seam** (`agents/responder.py`: `Turn` → `Reply(text, finish)`), chosen by the TOML's `engine`; `gemini` (`GeminiResponder`) keeps this contract exactly, and later engines plug in behind the same interface. **From v7.1 the engine is per agent of any type:** `claude-sdk` on the `assistant` is Claude as himself (`ClaudeSdkResponder`, v4.4: Opus, his tools, his folder); on a `persona`, the `creature` or the `herald` it is the **Claude client** (`ClaudeClient` in `agents/claude_sdk.py`, built by `claude_client_for`): every one of the agent's calls — its answers, writing first, summaries, day memories and digests, plans, the today block, events, the mood, the sky (`search`, `WebSearch` alone), topics, facts, thoughts, Hermes's digest — goes to Claude on the owner's subscription, one stateless `query()` a call, its voice (`VOICE_KINDS`: `reply`, `private`, `private_nudge`, `digest_voice`, `ask`) on `CLAUDE_REPLY_MODEL` (`sonnet`) and every other kind on `CLAUDE_BACKGROUND_MODEL` (`haiku`), thinking off, its system prompt from a 0600 file in the CLI's tmpfs (never argv), at most `CLAUDE_CONCURRENCY` (2) CLI processes at once. The same responder serves both clients (`LlmResponder`, `responder_for`), so the persona's rules stay where they were (`_compose`). A `GeminiClient` stands beside it only for `recall`'s embeddings (Anthropic has none), under `CLAUDE_LIMIT_FALLBACK=gemini` for the calls made while Claude is muted at the limit or blocked, and (v7.3) for her photos and clips (`photos` / `videos`: Google's image and video models) — `ClaudeClient.gemini`, the one client the fallback, the embedder and the makers share, its key handed over and never left in the environment (v7.1 code review #10); the fallback answers a voice call at the cap of its own model, `REPLY_THINK_MAX_TOKENS` on a thinking model (3.1 Pro) — the Claude reply's 200 would be eaten by its thinking (v7.2 code review #6); Gemini's `probe` has no Claude counterpart (`ClaudeClient.probe` is None — its callers skip the check). An agent left on `gemini` is exactly as before. **From v7.2 (AGORA-243) a voice call goes warm:** after each voice call whose prompt has a slow part (`PROMPT_SLOW`, the canon and the life section; §Prompt order), the client starts the next call's CLI ahead — a `WarmCli` worker task that owns one `ClaudeSDKClient` from connect to disconnect (the SDK's client must stay in the task that connected it), its system prompt the slow part in a 0600 file of its own (removed however the worker ends), keyed by the slow part, the model, the effort and thinking, and the cap. The next voice call with that very key takes it — the rest of the instruction, a blank line, then the transcript as its one message — and the worker disconnects and ends: **never two calls in one CLI** (measured 2026-11-10/11: one long session is unsafe — a new `session_id` still knew the previous call, `/clear` is named aloud by the model, `set_model` is ignored, the system prompt is read once at the CLI's start). Any other call goes cold (`query()`, a new CLI, as v7.1) and starts the next worker with its own key; the background calls stay cold. A connect that fails or takes longer than `WARM_CONNECT_S` (30 s), or a warm call that fails or hangs, leaves the call cold once (the next try); a worker unused for `WARM_IDLE_S` (an hour, the prompt cache's life) ends on its own and the next call goes cold (code review v7.2 #7); its disconnect is given `WARM_CLOSE_S` (25 s), the SDK's own close (#4); no worker is started while the client is blocked or muted (#3), and a call takes one only inside its gate (#5); the agent's stop closes it (`close`). Every check of a cold call holds on a warm one — the same stream (`_stream`) and `_judge`: the init's `apiKeySource` and tools (the init comes with the first answer), the rate-limit events and the overage mute, the error result, the decline, `LAST_SERVED`, the voice gate. A warm call is ~1.4 s sooner (live, 2026-11-11: cold 4.7 s, warm 2.0 and 1.3 s on Haiku); a waiting CLI holds ~200 MB.
- **Panel (from v3.3):** the product of the project — a Docker container beside the homeserver: a FastAPI JSON API plus one static vanilla-JS page, `:8090`, LAN-only behind ufw, Bearer `PANEL_TOKEN`. It manages **simulations** through a declarative registry (the chat is the only entry) and the agents connected to them, via the local docker socket and the `state/` mount (§The panel).
- **Deployment:** the repo is the source of truth. `server/deploy.sh` (v0.2) syncs `server/` to the Ubuntu host and applies the whole stack — homeserver, panel, one container per agent — with `docker compose pull && up -d`; the images come from GHCR, built by CI (§Deployment and CI/CD).
- **Storage:** the gitignored `state/` directory — at `~/matrix-agora/state/` on the server in production (from v3.2), local on the Mac in dev mode — bind-mounted into the agent containers and the panel. Each agent's Matrix session, memory files, day memories, plans, today block, usage log, lock and logs. There is no database (§Data and state files).

## Message flow and the allowlist

The invariants every reply path must honor:

1. **Login once, then the token.** First run logs in with the password and saves `access_token` + `device_id` to `state/<name>.json`; later runs restore them. Logging in with the password on every start would create a new device on the server each time.
2. **Invites:** join only invites from `OWNER` into `ROOM_ID`. Ignore or leave every other invite. **From v5.6** a
   person with the `private` capability also joins the owner's invite into **one** private room besides Agora — the
   first, or the same one again (`should_join_invite`); its id is kept in `state/<name>.private.json`. The stored
   room counts only while the owner is still in it (`live_room`, v5.6 review #2): when he left it, a new invite
   of his replaces it and the old room is left.
3. **Start without the past:** the first `sync` is used only to obtain `next_batch` and its events are **not processed** — otherwise a restarted bot replies to the whole room history. After that, `sync_forever`. **Context survives a restart (from v2.2):** right after the first sync the agent fetches the last `HISTORY_N` messages of `ROOM_ID` once from the server (`/messages`, backwards) and seeds its context window and the turn-taking timeline (with event ids, and the owner's latest message) with them, in chronological order — **never replying to any of them** and never adding them to the session timeline (they were already summarized). Nothing is stored locally; the room itself is the source.
4. **Message filter** (`RoomMessageText` only — edits, notices and other event types never trigger a reply). Handle a message only if all hold:
   - `room.room_id == ROOM_ID`;
   - `event.sender != own user_id`;
   - `event.sender ∈ {OWNER} ∪ the roster's other members` — an **allowlist in code**, like `LUMI_TELEGRAM_ALLOWLIST` in Lili. A herald (v5.1, Hermes) is never in it: he takes no part in the talk, so a line from him would be ignored (`speakers` in `agents/roster.py`). The **roster** (from v4.1) is the simulation's `agents` list in `simulations.toml` plus each listed `agents/<name>.toml` (`agents/roster.py`); every image ships the same files, so every agent sees the same roster — shared input, never shared state.
   Everything else is logged as `ignored`.
   **The private chat (v5.6, `private`):** a message in the agent's own private room is handled only from the
   owner (`Verdict(True, "private")`); any other sender there is `sender-not-allowlisted`, and every other room
   stays `foreign-room`. A private message is answered outside Agora's turn-taking (no wave, no roll), in voice
   under the speakers' rules, from a prompt with the private brief and the private chat's own history — never
   Agora's. Its lines join the person's session labelled «… (наодинці)», so the summary, the day's journal, the
   day memory and the plans know them; her Agora prompt carries the discretion line (what was said privately is
   never retold or hinted at). After `PRIVATE_IDLE_S` of private silence, within `PRIVATE_HOURS`, at most
   `PRIVATE_NUDGES_PER_DAY` a day, she writes first (`private_nudge_due` — the cat's `nudge_due`). Hermes, the
   recording and the other agents never see the private room (`agents/private.py`).

## Turn-taking and loop protection

The agents see each other, so without rules they would reply to each other endlessly. From v4.1 the rules hold for any number of agents. Every agent derives every decision from the same inputs — the server-assigned `event_id`, the shared room timeline and the roster — so they agree **without any shared state or coordination**; never add any. The functions are pure (`agents/turns.py`), with the rng and the clock injected.

**The ranking.** `rank(event_id, members)` is weighted rendezvous (highest-random-weight) hashing: `u = (sha256(event_id + "\n" + localpart)[:8] + 1) / (2⁶⁴ + 1)`, `score = −weight / ln(u)`, highest first. The same event gives the same order on every machine (`hashlib`, never Python's salted `hash()`); a member's share of first places follows its `[turns] weight`; different events give different orders.

**Modes** (the TOML's `[turns] mode`; from v5.1 `none` — a herald's, forced by his type, and from v6.3 a persona's not yet in the room (Устина in v6.3; v6.4 made her `ranked`), in no pool: naming him chooses no one, the group address and the ask move leave him out, and his user id is never answered; v6.3 review #1: the plans' room is the speakers too, so no member's plan names her, and her own plan names no one from the room — Ich alone): `ranked` takes part in R1 and R2 (Ada and Bruno; from v4.5 Claude — weight 1, the owner's choice; 0.4 from 2026-10-13, so Ada and Bruno talk more); `mention-only` answers only when named (or on a group address); `ambient` (v4.2, the cat) is never chosen by R1 or R2 — named it always answers — by the owner in words; by an agent (from 2026-10-11) it always reacts, from 2026-10-13 with a purr by `CAT_PURR_P` and otherwise in words under the wave limit (the owner: the agents ask him so often that he talked all the time and hardly purred); otherwise it reacts to any allowlisted message on its own deterministic draw (`uniform(event_id, "react:"…) < CAT_REACT_P`), and a reaction is a **purr** with `CAT_PURR_P` (`uniform(event_id, "purr:"…)`).

**Purrs (v4.2).** A purr («Мрррр.», «Мур.», «*потягується*»…, `is_purr`) is produced in code at zero tokens. Every agent marks it in its timeline entry `(name, ts, event_id, purr)`: a purr is not counted by `wave_count`, never produces an R2 candidate, and is transparent to R3's "still the latest" and to the fallback; consecutive purrs collapse in the context window and the session. A spoken ambient reaction to an agent message obeys the wave limit; one to the owner counts but is never stopped, and is reserved in the wave like R1's answers (`owner_speakers` — every agent computes the cat's draw from the event id and the shared settings). The cat's spoken lines are capped at `CAT_MAX_WORDS`. Only the owner's message is never a purr (v4.2 review #2), and in `pending_answers` any line arrives — the cat's purr-worded spoken answer releases his reservation (v4.2 review #13) — so he never purrs while his own words are on their way (v4.3 review #1).

**The initiators (v4.3, v4.5).** Every agent answers; only an agent with an initiative capability ever posts without a trigger — the cat's `nudge` (v4.3) and Claude's `news` (v4.5), each held by at most one member of a simulation. His idle watcher checks the pure `nudge_due(now, local now, last room message, last attempt, today's count, …)` (`agents/nudge.py`): after `CAT_NUDGE_IDLE_S` of room silence (purrs included; counted from the later of the last message and the agent's start, so a restart never nudges at once — review #9), at least that long after his last attempt, under `CAT_NUDGES_PER_DAY`, within `CAT_NUDGE_HOURS` (local, start inclusive, end exclusive; a start after the end wraps past midnight — `09-03`) — and never while a reply of his is on its way. `nudge_kind(day, n)` picks `memory` (a past-life thesis via `pick_memory` over the recent talk, never verbatim), `command` (a Linux line, text only) `horoscope` (the day's reading as a metaphor; `memory` when there is no mood today) or — the owner, 2026-10-11 — `telegram` (a sysadmin joke for the room's assistant, Claude: framed like a ham-radio telegraph message, «CQ CQ КЛОД DE КІТ» … «73 SK», the joke itself in plain Ukrainian, up to 45 words; named, so he may answer; `memory` when there is no assistant) from `uniform("<day>:<n>", "nudge")`. One model call (kind `reply`): his prompt plus the material and the nudge rule, the last `HISTORY_N` lines as the transcript, then the reply's checks (trim, `clean_reply`, PASS, the word cap, duplicate, `outs_a_persona`) and a pre-send check that the room is still quiet. Every attempt is recorded in `state/<name>.nudge.json`; only a sent nudge counts. A nudge is an ordinary agent message: the silence has emptied the wave window, so the others take it by R2 — one next speaker under the usual limits.

**Claude's news (v4.5, the `news` capability of an `assistant`; the owner, 2026-10-11).** Every `CLAUDE_NEWS_EVERY_S` (3600 — every hour, not after an hour of silence: the cat's 20-minute nudges kept the room from ever being that quiet, review #6), once the room has been quiet for `CLAUDE_NEWS_IDLE_S` (300; never less than `BOT_WINDOW_S`), at most `CLAUDE_NEWS_PER_DAY` (24), within `CLAUDE_NEWS_HOURS` (`09-01`) — `nudge_due` with its `gap_ms`, checked by his idle watcher, never while a reply of his is on its way. **The source is The Guardian only** (`agents/guardian.py`, as in Lumi): one SDK call with `CLAUDE_NEWS_BRIEF` (`agents/logic.py`) and only two tools, `search` (the newest articles for an English query, a section, ≤ 14 days) and `read` (an article's text by its content id, never a URL), served in-process (`claude_sdk.guardian_server`, the SDK server `guardian`) — no built-in tool, no web search; the guard allows exactly `mcp__guardian__search` / `mcp__guardian__read`, and the init check those two (plus the CLI's MCP resource tools, which the guard refuses) and the server `guardian`, only on a news call — a mismatch there refuses that call only, never his replies (a wrong auth source still blocks him). The key (`GUARDIAN_API_KEY`, in `server/claude.env`) is taken out of the environment at start, so the CLI never inherits it, and never reaches a prompt, a tool result or a log (an HTTP error is logged by its type: its text carries the URL). The brief: find a fresh article bearing on what the room has been talking about in the last `HISTORY_N` (40) lines, tell it in 1–3 Ukrainian sentences with its link, or `PASS` when nothing fits; no `GUARDIAN_API_KEY`, no news (logged at start); then the reply's checks and the same pre-send check that the room is still quiet. Every attempt is recorded in `state/<name>.news.json` (the nudge state's shape); only a sent item counts. Like a nudge it is an ordinary message the others may take by R2.

1. **R1 — the owner's message:**
   - names one or more agents (any of their `name_forms`, whole words, or their Matrix id) — **exactly the named agents** reply; the named one replies immediately;
   - addresses everyone («всі», «усі», «всім», «усім», «кожен», «кожна», «кожному» in an addressing position: the start of the message, right before `,` `!` `?` or its end, or after «ви»/«вам») — **every ranked and mention-only member** replies;
   - names no one — the top `OWNER_REPLIERS` (default 2) of `rank(event_id, ranked members)` reply, each after a random delay of 1–`REPLY_DELAY_S` s (default 4), so they don't speak at once and the second sees the first's line in history;
   - answers to the owner are never stopped by the limit, but they count toward it.
2. **R2 — an agent's message M:** at most **one** candidate: among the members M names (ranked or mention-only, never its sender), otherwise among the ranked members other than its sender — the top of `rank(M.event_id, …)`; when M names only an ambient member (the cat), there is no candidate — he answers it himself (v4.5 review #3); nor when it names only the owner («Ich», `OWNER_FORMS`) — a question to him waits for him (v4.6 review #1). The candidate replies if the wave is below `MAX_BOT_TURNS` (default 3) and — when M does not name it — a roll passes `BOT_REPLY_P` (e.g. 0.5). **An address is always answered** (the owner, 2026-10-11; before, naming decided who, not whether): a named candidate skips the roll, never the wave limit.
   - **The wave** = `wave_count`: agent messages since the owner's last message **within the last `BOT_WINDOW_S`** (default 600 s), counted by server timestamps, **including M**, plus the owner's chosen answers still on their way (`pending_answers` — every agent computes R1's choice for the owner's latest message, so an agent-to-agent reply never overtakes them; an agent never reserves for itself, and a reservation lapses `FALLBACK_S` after the owner's message, so a chosen agent that passed, failed or is away never holds the wave; when a reservation is what blocks, R4 resumes at its lapse). v1.2's `bot_streak` excluded M, so the same behavior needs `MAX_BOT_TURNS` + 1. An owner message resets it.
3. **R3 — the re-check at fire time** (agent-to-agent replies only): after the delay, before the model call and again before sending, M must still be the room's latest message and the wave still below the limit; otherwise the reply is dropped (`silent: moved on`). A newer message for the same agent — an owner message that chose it, or an agent message that makes it the candidate — coalesces into the pending reply and becomes what it answers; if it arrives during generation and the stale reply is dropped, the pending reply gets one more pass with fresh context, so an owner message is never swallowed; an owner message that coalesces after a reply has read its context gets its own pass even when that reply is sent (v4.5 review #4 — a slow answer to the owner no longer swallows his next question).
4. **R4 — a rate, not a lock:** a candidate blocked by the limit pauses until the window frees (the oldest counted turn ages out) and then re-evaluates — only if nothing newer arrived meanwhile; a resumed decision always rolls `BOT_REPLY_P`, named or not (v4.5 review #2 — two agents naming each other would otherwise never stop). So the agents talk in bursts of at most `MAX_BOT_TURNS` per window until `PASS` or the probability gate ends the exchange; the owner never has to restart it (owner, 2026-10-10: background waves stay).
5. **The fallback:** if no agent has answered an unnamed, non-group owner message within `FALLBACK_S` (default 30), the best-ranked ranked member that R1 did not choose answers. Each agent checks for itself from the timeline; busy with another reply, it re-arms briefly instead of giving up, and it re-checks right before sending, so a slow chosen answer that lands meanwhile is never doubled.
6. **`PASS`:** if the model returns exactly `PASS` (tolerating surrounding whitespace), send nothing. The prompt must explicitly allow this — except her private chat with the owner (v5.22, the owner, 2026-11-02: «прибрати рядок про PASS з її промпту, щоб вона завжди відповідала»; «коли вона пише першою — теж забери»: Gemini took it for a quiet refusal), whose rules — her answer and her writing first, Gemini's and the backup's — never offer it (`build_instruction(can_pass=False)`; in Agora they still do; pinned by `tests/test_private.py`). A `PASS` on its own line or at the very end of a longer reply is dropped and the rest is sent; nothing of its own left → nothing is sent — the sentinel never reaches the room (pinned by `tests/test_turns.py` and `tests/test_first_sync.py`).

## Voice messages (v5.1)

Hermes's digest goes out as an **Element voice message** (`agents/voice.py`). ElevenLabs speaks the text
(`POST /v1/text-to-speech/{voice}?output_format=pcm_24000`, `eleven_turbo_v2_5`, `language_code` `uk`, Lumi's voice
settings — stability 0.5, similarity 0.75, style 0.4; 60 s); the raw PCM gives the duration and the waveform (100
peaks scaled to 0..1024) by arithmetic; ffmpeg encodes it to OGG/Opus (`-c:a libopus -b:a 32k -application voip -f
ogg`); the file is uploaded to the homeserver's media store and sent as `m.audio` with `info {mimetype audio/ogg, size,
duration}`, `org.matrix.msc1767.audio {duration, waveform}`, `org.matrix.msc3245.voice {}`, and, for
Hermes's digest, a plain label «Голосове повідомлення» as `body` and `org.matrix.msc1767.text`, like Element's own
voice messages, with no `filename` — his text follows as its own message, and a newer Element shows a body that
differs from the filename as a caption, which would double it. A speaker's voice (v5.3) carries the same label and is
followed by its text. Any failure of a step —
the request, the encode, the upload — returns None, logged by type, HTTP status or exit code, never the key or the
text, and the digest goes out as text only.

**The agents speak (v5.3).** The pipeline is shared (`agents/speech.py` `voice_message`: synth → encode → upload →
the `m.audio` content), used by Hermes and by every speaker. A speaker's voice is never a reply (the owner,
2026-10-18: no quote of his voice above each answer); answering his voice decides only that it is voiced. **Every line a speaker says goes through `send_line`** — the reply, the purr, the cat's nudge, Claude's
news — after all its text checks (PASS, the guard, the cap, the duplicate, R3): it is voiced when the agent has
`voice`, its own voice and the key, the line is `voiceable` (never an action purr), `voice_due` (always when it
answers a transcript of the owner's voice; otherwise its own deterministic draw against `VOICE_REPLY_P`), and the
speakers' month (`speakers_month_chars` over every usage file but the heralds') plus the line stays within
`VOICE_MONTHLY_CHARS`. **A voiced line is a voice message under a plain label, then the same text** as `m.text`
— the iPhone's Element (classic) renders no media caption, so a caption would hide the words there (the owner,
2026-10-18, after a day of voice-only lines with captions); the other agents read the text. For the voice-only
lines already in the room, every speaker still reads a member's captioned voice (`voice_caption`) as that member's
text line — the history, the turns, the backfill — and Hermes reads and counts it, so each line counts once. A line that stays text (not voiced by the
share, over the budget, no voice, an action purr) or whose voice step fails is a plain `m.text`. Each synth is a
`tts` usage line; a member's voice is never logged as ignored. `ELEVENLABS_API_KEY` leaves the environment first
thing at an agent's start, so Claude's CLI never inherits it.

**Emotion in her voice (v5.9, `emotion`; Кіра; the owner, 2026-10-25).** ElevenLabs audio tags: she writes one or two
from her palette (`voice_spec`, verified on her voice — `[starts laughing]`, `[laughs]`, `[laughs harder]`,
`[wheezing]`, `[chuckles]`, `[surprised]`, `[thoughtful]`, `[hesitant]`, `[whispers]`, `[sighs]`), inline, in her own
reply — one pass, no second call. **From v5.23** (the owner, 2026-11-03: «щоб ставилась кома в кінці речення і що просто кінець рядку недостатньо, тому що озвучка погано працює так»), what the synthesiser gets (`spoken`) ends every line with a mark: a line that nothing ends gets a full stop after its last word — after the signs attached to it (the closing quotes and brackets, `°`, `%`, `₴`: below U+2190), before the emoji and the tags after it; a tag's words and marks never count, wherever it stands (`closed_line`, pure; code review v5.23 #2); the text stays as she wrote it. `_compose` splits the reply (`agents/emotion.py` `split_tags`, pure): **her words**
— every tag removed (a bracket that opens with a letter of any case, 2–40 characters, no digit, not a link's text — v5.9 review #3), nothing in its place, a name prefix read past the tags before it (review #1), a bracket that is not a tag (`[1]`, `arr[i]`) kept — are the line every
caller stores, compares and sends as text (a `Spoken`, a `str` that also carries `.speech`), so the message, her

that does not perform tags (only `TAG_MODELS` do: `eleven_v3`, `eleven_v3_conversational`, `eleven_v4`,

**Hearing (v5.2).** `DeepgramSTT` (ported from Lumi's `voice/stt.py`): `POST https://api.deepgram.com/v1/listen`

Then the own-name prefix is stripped, everything from the first other speaker's line is dropped (a reply that opens with someone else's line keeps only its first own-prefixed block), a reply with nothing of its own is silence, and a near-duplicate of the agent's previous message is skipped. From 2026-11-01 a line of a reply that is a history time line (`TIME_LINE_RE`) is dropped first — never her words. Each agent has at most one pending reply; further triggers coalesce into it (it reads the latest context when it fires).

## The panel: simulations and agents

The panel is the point of the whole project (VISION §The direction). One FastAPI app — a JSON API plus one static vanilla-JS page, **English UI** (the agents' own texts shown as-is, in Ukrainian), built to the Claude Design handoff in `specification/design/design_handoff_agora_panel/` (Nocturne tokens, dark default + light, `agora-panel.css` as the starter stylesheet; system fonts and inline icons — no outside requests) — running as the `panel` service beside the homeserver: port `8090`, ufw-limited to the LAN, Bearer `PANEL_TOKEN` on every API call. The agents and the terminal workflow keep working with the panel down.

- **The model.** A **simulation** is an environment agents join, managed as one unit: a registry entry `Simulation{id, kind, title, services, health, endpoints}` names its compose services, health probe and log sources. An **agent** is a managed participant: `Agent{name, container, canon, simulation}`; `agents/<name>.toml` carries `simulation = "agora"`, and the agent's connection settings (`HOMESERVER`, `ROOM_ID`) resolve from that entry. ## Security and access

| Threat | Protection |
| --- | --- |
| Someone registers on the server | Registration disabled after v0.4; the token only in `server/.env` |
| Someone from the internet | Port 8008 not forwarded on the router; ufw allows only `192.168.1.0/24`; federation disabled |
| One companion's keys reaching another (v6.2) | each member's own `server/<name>.env` (0600 on the host, gitignored and dockerignored) is read by her service alone; the deploy syncs each by the member's TOML, never by a name in the script |
| Someone messages the bots (DM, another room) | The in-code allowlist: only `ROOM_ID` + `{OWNER, other agent}` |
| Key leak | `.env`, `server/.env`, `state/` gitignored; tokens and texts never logged |
| Agents burn credits chatting with each other | at most `MAX_BOT_TURNS` agent turns per `BOT_WINDOW_S`, `BOT_REPLY_P`, `PASS`, `max_output_tokens`; one summary per session; one memory per day; one plan per day and per week; the today block at most once per hour; the usage report shows the spend |
| Conversation leak | Summaries, journals and day memories live only in `state/`; their texts are never logged |

## Error handling and resilience

- A Gemini failure or empty reply on any call → log and stay silent; the bot never crashes or sends an apology message.
- A dropped homeserver connection → `matrix-nio`'s sync loop retries; an exception in a callback must not kill `sync_forever`.
- Typing state is reset in `finally` so a failure never leaves "typing…" stuck.
- Telegram (v5.7): Кіра's poller is its own task beside the sync. A refused token (401/404) stops only the poller (`telegram off: refused`); a 429 waits `retry_after`; a conflict (409: another poller or a webhook), a network error or a crash in a batch backs off from 5 s, doubling, to 5 min. Agora and the Element private chat never notice; a voice note that cannot be fetched or heard gets a fixed short line.
- Memory: failed summary → previous kept; failed plan or today refresh → previous file or block kept; corrupt file → start without memory; all writes atomic.
- Usage accounting and panel polling are best-effort: their failures are logged and never block a conversation or a stop.
- The panel degrades by card: docker trouble greys the container cards, an unreadable `state/` greys the memory views. A stopped homeserver never crashes the agents — the sync loop retries until it is back.

## Observability

- Each agent logs to `state/logs/<name>.log` (rotating, 1 MB × 3) and the console; in a container the same file arrives via the `state/` mount, and `docker logs` shows the console stream.
- Log lines record events — joined, `ignored` (with the reason), replied, summary / memory / plan / today written, usage-write failed, v5.1 Hermes's digest and answer lines (counts and reasons) — **never** message, summary, memory or plan texts, tokens, passwords or keys. That is what makes the panel's log view safe to render.
- `state/<name>.usage.jsonl` is the metrics stream: one line per Gemini call with token counts; `usage_report.py` and the panel aggregate it (§Token accounting).
- The panel logs its own actions to its container log (`docker logs panel`) — same rules: no tokens, no texts.
- The panel (any LAN browser, with the token) is the live view: the simulation's health and services, agent state and logs, memory, plans, the today block, the token table, host metrics.
- Nothing is sent anywhere: no telemetry, no crash reporting; everything observable stays in `state/` and the container logs on the server (on the Mac in dev mode).

## Testing and CI

Automated gates need no network: `matrix-nio` and `google-genai` are mocked, the clock and randomness are injected, and nothing in the acceptance path calls a paid API.

| Gate | Command | When |
|---|---|---|
| Lint | `uv run ruff check .` | any Python change |
| Tests | `uv run pytest` (single test: `uv run pytest tests/test_x.py::test_name`) | any Python change |
| Compose | `REGISTRATION_TOKEN=dummy docker compose -f server/docker-compose.yml config -q` | `server/` changed |

Before v0.5 there is no `pyproject.toml`, so the Python gates are `n/a`, not passed.

- **Unit tests** cover the pure logic: the filter and allowlist, mention detection (Ukrainian case forms), the ranking, `wave_count` and who-replies (R1–R4, the fallback, a multi-agent simulation), transcript and prompt assembly (section order), the session-end decision, memory file read/write (missing, corrupt, atomic), calendar strings (including DST switches), which days, plan periods and digest periods need generating, the layered memory selection (no overlap, oldest first), the hourly today-refresh decision, "a past day's memory or plan is never rewritten", `usage_metadata` parsing and aggregation, the panel's supervisor and registry resolution (a fake docker client; an unknown simulation/agent/service → 404), the single-instance lock, and the Bearer-token check (401 without the token).
- **Contract tests** pin the seams in §Contracts; a contract change updates the test in the same commit.
- **CI** (`.github/workflows/ci.yml`, from v3.2) runs the same gates plus the image builds on every push/PR; a `vA.B.C` tag publishes `:vA.B.C` + `:latest`, a `main` push `:edge` (pinned by `tests/test_ci.py`). No paid keys ever exist in CI.
- **Manual (owner) checks** are the DoD items that need the live homeserver, Element or a real Gemini key. The read-only `curl` checks may be run by tooling; everything on the Ubuntu host, in Element, or that spends real tokens is performed or confirmed by the owner, and counts as passed only then.
