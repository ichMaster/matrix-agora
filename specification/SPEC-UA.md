# matrix-agora — специфікація PoC

Власний Matrix-сервер у домашній мережі, де в одній кімнаті розмовляють **ти і два прості LLM-агенти** (Gemini 2.5 Flash). Агенти бачать і тебе, і одне одного; ніхто ззовні писати їм не може.

Мета PoC — перевірити саму схему (сервер → клієнт → боти → розмова втрьох) перед тим, як підключати до неї справжніх агентів на кшталт Лілі. Простота важливіша за повноту.

## 1. Архітектура

```
 ┌──────────────── Ubuntu server 192.168.1.197 ────────────────┐
 │  Docker: continuwuity (Matrix homeserver)  :8008  (HTTP, LAN) │
 │  server_name = agora.lan, федерація OFF, шифрування OFF       │
 └───────────────▲──────────────────▲──────────────────▲────────┘
                 │ Client-Server API (http://192.168.1.197:8008)
     ┌───────────┴───┐     ┌────────┴────────┐  ┌──────┴──────────┐
     │ Element Desktop│     │ agent "Ада"     │  │ agent "Бруно"   │
     │ (ти, @me)      │     │ Python + nio    │  │ Python + nio    │
     └────────────────┘     │ → Gemini API    │  │ → Gemini API    │
                            └─────────────────┘  └─────────────────┘
                 Mac (клієнт і обидва агенти працюють тут)
```

- **Сервер:** [Continuwuity](https://continuwuity.org) — Matrix homeserver на Rust: один контейнер, вбудована БД (RocksDB), без Postgres.
- **Клієнт:** Element Desktop на Mac. Саме Desktop, а не app.element.io: веб-версія працює по HTTPS і не під'єднається до HTTP-сервера в LAN (mixed content).
- **Агенти:** два процеси Python на Mac, один і той самий код, різні конфіги (ім'я, персона, акаунт). Бібліотеки `matrix-nio` (Matrix) + `google-genai` (Gemini).
- **Панель (з фази 9):** локальна веб-панель на Mac (`127.0.0.1`) для запуску агентів і адміністрування.
- **TLS:** немає, бо це PoC у домашній мережі. Доступ ззовні — тільки пізніше через Tailscale, порт у роутері **не відкривати**.

Імена агентів «Ада» і «Бруно» — умовні, заміни на свої.

## 2. Фаза 0 — сервер (Ubuntu, 192.168.1.197)

### Задачі

1. Встановити Docker Engine + compose plugin (офіційний репозиторій Docker для Ubuntu).
2. Створити `~/matrix-agora/server/docker-compose.yml` (у репозиторії — `server/docker-compose.yml`):

   ```yaml
   services:
     homeserver:
       image: forgejo.ellis.link/continuwuation/continuwuity:latest
       # дзеркало, якщо основний реєстр недоступний: ghcr.io/continuwuity/continuwuity:latest
       restart: unless-stopped
       ports:
         - "8008:8008"
       volumes:
         - db:/var/lib/continuwuity
       environment:
         CONTINUWUITY_SERVER_NAME: agora.lan        # НЕ можна змінити без стирання БД
         CONTINUWUITY_DATABASE_PATH: /var/lib/continuwuity
         CONTINUWUITY_ADDRESS: 0.0.0.0
         CONTINUWUITY_PORT: 8008
         CONTINUWUITY_ALLOW_FEDERATION: "false"     # повністю закритий від мережі Matrix
         CONTINUWUITY_ALLOW_ENCRYPTION: "false"     # жодних E2EE-кімнат — ботам так простіше
         CONTINUWUITY_ALLOW_REGISTRATION: "true"    # тимчасово, на фазу 2
         CONTINUWUITY_REGISTRATION_TOKEN: "${REGISTRATION_TOKEN}"
   volumes:
     db:
   ```

   `REGISTRATION_TOKEN` лежить у `server/.env` поруч (довгий випадковий рядок, `openssl rand -hex 24`), у git не потрапляє.
3. Firewall: `sudo ufw allow from 192.168.1.0/24 to any port 8008 proto tcp` — порт доступний лише з домашньої мережі.
4. `docker compose up -d`, перевірити логи: `docker compose logs -f homeserver`.

`server_name` — це лише «домен» в іменах користувачів (`@ada:agora.lan`). DNS для нього не потрібен, бо клієнти ходять на `http://192.168.1.197:8008` напряму. Якщо IP сервера колись зміниться, зміниться тільки URL у конфігах, імена лишаться.

### DoD

- З Mac: `curl http://192.168.1.197:8008/_matrix/client/versions` повертає JSON зі списком версій.
- `curl http://192.168.1.197:8008/_matrix/federation/v1/version` не відповідає як федерація (федерація вимкнена).
- Після `sudo reboot` сервера контейнер піднімається сам.

## 5. Фаза 3 — echo-бот (Matrix без LLM)

Мета — перевірити Matrix-частину окремо від LLM.

### Структура проєкту

```
matrix-agora/
  SPEC.md
  README.md
  pyproject.toml            # uv; deps: matrix-nio, google-genai, python-dotenv
  server/
    docker-compose.yml
    .env.example            # REGISTRATION_TOKEN=
  agents/
    agent.py                # один код для обох агентів
    ada.toml                # name, user_id, persona, …
    bruno.toml
  .env.example              # HOMESERVER, ROOM_ID, OWNER, ADA_PASSWORD, BRUNO_PASSWORD, GEMINI_API_KEY
  state/                    # access token + device_id кожного бота (gitignored)
```

Запуск: `uv run agents/agent.py agents/ada.toml` (і так само для `bruno.toml` в окремому терміналі).

### Поведінка

1. **Логін:** перший запуск — логін паролем, `access_token` + `device_id` зберегти в `state/<name>.json`. Наступні запуски — з токена (інакше кожен старт створює новий «пристрій» на сервері).
2. **Інвайти:** приймати (`join`) **лише** запрошення від `OWNER` у кімнату `ROOM_ID`. Інші — `leave`/ігнор.
3. **Старт без минулого:** перший `sync` лише для отримання `next_batch` — події з нього **не обробляти** (інакше після рестарту бот відповість на всю історію). Далі — `sync_forever`.
4. **Фільтр повідомлень** (`RoomMessageText`), обробляти тільки якщо всі умови виконані:
   - `room.room_id == ROOM_ID`;
   - `event.sender != власний user_id`;
   - `event.sender ∈ {OWNER, user_id іншого агента}` — **allowlist у коді**, як `LUMI_TELEGRAM_ALLOWLIST` у Лілі.
5. **Echo:** відповісти `"<name> чує: <text>"`.

### DoD

- Ти пишеш у «Агору» — обидва боти відповідають echo.
- Рестарт бота — він не відповідає на старі повідомлення і не створює новий device.
- Повідомлення в іншій кімнаті / в DM бота — ігнорується (видно в лозі як `ignored`).

## 6. Фаза 4 — LLM (Gemini 2.5 Flash)

### Задачі

1. Замінити echo на виклик Gemini через `google-genai` (async):

   ```python
   from google import genai
   from google.genai import types

   client = genai.Client()  # бере GEMINI_API_KEY з оточення
   resp = await client.aio.models.generate_content(
       model="gemini-2.5-flash",
       contents=transcript,  # див. нижче
       config=types.GenerateContentConfig(
           system_instruction=persona,
           max_output_tokens=400,
           thinking_config=types.ThinkingConfig(thinking_budget=0),  # швидше й дешевше для чату
       ),
   )
   reply = resp.text
   ```

2. **Контекст:** кожен агент тримає в пам'яті останні `HISTORY_N` (напр. 30) повідомлень кімнати з `sync` — **включно з власними та іншого агента**. У модель вони йдуть одним текстом `"Ім'я: текст"` по рядку + інструкція: «Ти — <name>. Відповідай лише від себе, коротко, без префікса з іменем».
3. **Персона** — у `<name>.toml`: 3–5 речень характеру, щоб агенти помітно відрізнялися.
4. **Typing:** `room_typing(room_id, True)` перед викликом Gemini, `False` після.
5. **Помилки:** якщо Gemini впав або повернув порожнє — лог + коротке службове повідомлення не надсилати (мовчати); бот не падає.
6. Надсилати як `m.text` (не `m.notice`) — інакше інший агент може вважати це службовим повідомленням.

### DoD

- Ти пишеш — кожен агент відповідає у своєму характері, з урахуванням попередніх реплік.
- Поки агент думає, в Element видно «друкує…».
- Без `GEMINI_API_KEY` або з невалідним — бот живий, пише помилку в лог.

## 7. Фаза 5 — розмова втрьох і захист від зациклення

Агенти бачать одне одного, тож без правил вони відповідатимуть одне одному нескінченно.

### Правила, хто відповідає

1. **Твоє повідомлення:**
   - згадує одного агента (ім'я або mention) — відповідає **тільки він**;
   - нікого не згадує — відповідають **обидва**, кожен після випадкової затримки 1–4 с (щоб не говорити одночасно, і другий уже бачив репліку першого в історії).
2. **Повідомлення іншого агента:** відповідати, лише якщо `bot_streak < MAX_BOT_TURNS` (за замовчуванням **2**), і з імовірністю `BOT_REPLY_P` (напр. 0.5) — щоб розмова не була механічною.
   - `bot_streak` — кількість повідомлень агентів поспіль **після твого останнього** повідомлення. Обидва агенти рахують його з однієї й тієї ж стрічки кімнати, тож рахунок узгоджений без жодної координації.
   - Твоє повідомлення скидає `bot_streak` у 0.
3. Агент може вирішити «тут нічого додати»: якщо модель повернула рівно `PASS`, нічого не надсилати (дозволити це в інструкції).

### Налаштування

У `.env` / toml: `MAX_BOT_TURNS`, `BOT_REPLY_P`, `HISTORY_N`, `REPLY_DELAY_S`.

### DoD

- Ти пишеш одне повідомлення без згадок — максимум `2 + MAX_BOT_TURNS` реплік агентів, далі тиша, доки ти не напишеш знову.
- «Адо, що думаєш?» — відповідає тільки Ада.
- Агенти посилаються на репліки одне одного (видно, що вони бачать одне одного).

## 8. Фаза 6 — канони агентів і пам'ять між сесіями

Зараз агент знає про себе лише 3–5 речень персони і пам'ятає розмову, тільки поки працює процес. Фаза 6 дає кожному агенту **канон** — стабільний опис того, хто він, — і **пам'ять про минулу сесію**: короткий підсумок останньої розмови, який після рестарту йде в промпт.

### Канони

1. **Канон** — markdown-файл у репозиторії, джерело істини про агента:
   - `agents/canon/common.md` — спільне для обох: що це за кімната, хто власник (`OWNER`), хто інший агент, мова й тон розмови;
   - `agents/canon/<name>.md` — особисте: характер, манера мовлення, інтереси, ставлення до власника й до іншого агента, чого агент ніколи не робить.
   - Канони описують агентів як **людей**: Ада і Бруно вважають себе людьми й не знають, що вони LLM-агенти. Це гра власника в закритій кімнаті — він єдиний співрозмовник і знає правду, сторонніх, яких можна ввести в оману, немає. Якщо колись до кімнати додадуться інші люди, це правило треба переглянути.
2. Канон **замінює** поле `persona` з фази 4: у `<name>.toml` замість нього — `canon = "agents/canon/<name>.md"`.
3. Канон читається один раз на старті. Якщо файлу немає або він порожній — бот не стартує і пише зрозумілу помилку.
4. Правила формату відповіді (лише від себе, без префікса з іменем, дозвіл на `PASS`) лишаються **в коді**, а не в каноні, щоб їх не можна було випадково зламати, редагуючи канон. Ці правила, промпти підсумків і спогадів не згадують, що агент — модель чи бот.
5. Канони лежать у публічному git, тож у них **немає секретів і приватних даних** власника.

### Пам'ять сесії

1. **Сесія** — відрізок розмови в кімнаті. Вона закінчується, коли в кімнаті тиша довше за `SESSION_IDLE_S` (напр. 900 с) або коли бота зупиняють (Ctrl+C / SIGTERM).
2. **Стрічка сесії** — усі повідомлення кімнати з моменту останнього підсумку, окремо від `HISTORY_N`. Якщо їх стає більше за `SESSION_MAX_MESSAGES` (напр. 200), підсумок робиться раніше, а стрічка очищається.
3. **Підсумок:** наприкінці сесії, якщо з минулого підсумку були нові повідомлення, агент робить окремий виклик Gemini: попередній підсумок + стрічка сесії → новий підсумок до `SUMMARY_MAX_WORDS` (напр. 200) слів. Так старі теми не зникають одразу, а стискаються.
4. **Зміст підсумку** — від першої особи агента, мовою розмови: про що говорили, що вирішили, що власник розповів про себе, які питання лишилися відкритими, що агент пообіцяв.
5. **Зберігання:** `state/<name>.memory.md` (папка `state/` — у `.gitignore`). Запис атомарний (тимчасовий файл + rename), щоб обрив не лишив пів-файлу.
6. **Промпт:** `system_instruction` = канон (спільний + особистий) + розділ «Що ти пам'ятаєш з минулої розмови: <підсумок>» + правила формату відповіді. `contents`, як і раніше, — останні `HISTORY_N` повідомлень.
7. **Старт:** підсумок читається з файлу. Перший `sync`, як і раніше, не обробляється — пам'ять береться з підсумку, а не з історії кімнати.
8. **Помилки:** якщо Gemini не зміг зробити підсумок — лишається попередній, пишеться лог, бот не падає. Пошкоджений файл пам'яті — бот стартує без пам'яті й пише про це в лог.
9. Кожен агент підсумовує **сам, зі своєї точки зору**: підсумки Ади і Бруно можуть відрізнятися, і це нормально.
10. Під час зупинки підсумок робиться з таймаутом (напр. 20 с), щоб Ctrl+C не зависав.

### Налаштування

У `.env` / toml: `SESSION_IDLE_S`, `SESSION_MAX_MESSAGES`, `SUMMARY_MAX_WORDS`.

### DoD

- «Адо, хто ти?» — відповідь узгоджується з `agents/canon/ada.md`, Ада говорить про себе як людина; Бруно на те саме відповідає за своїм каноном.
- Поговорити на якусь тему й зупинити обох агентів — з'являються `state/ada.memory.md` і `state/bruno.memory.md`, не довші за `SUMMARY_MAX_WORDS` слів, без токенів і паролів.
- Без зупинки: після `SESSION_IDLE_S` тиші підсумок оновлюється сам.
- Після рестарту: «Про що ми говорили минулого разу?» — кожен агент згадує тему.
- Gemini падає під час підсумку — старий підсумок цілий, бот живий.
- Файли пам'яті не потрапляють у git; тексти повідомлень і підсумків не логуються.
- Юніт-тести без мережі (Gemini замоканий): збирання промпту (канон + підсумок + правила), рішення «сесія закінчилась», читання й запис файлу пам'яті (файлу немає, файл пошкоджений, атомарний запис).

## 9. Фаза 7 — обізнаність про світ (world awareness)

Агенти знають, де вони і котра година, і пам'ятають минулі дні — по днях. Усе це йде в промпт; спогади генеруються автоматично, руками їх ніхто не пише.

### Місце і час

1. **Місце:** агенти живуть у Львові. `LOCATION` (за замовчуванням «Львів, Україна») і `TIMEZONE` (`Europe/Kyiv`) — у `.env` / toml.
2. **Календар і час:** перед кожним викликом Gemini код рахує поточний момент у `TIMEZONE` і додає в промпт дату, день тижня, час, частину доби (ранок / день / вечір / ніч) і пору року — українською, напр. «Зараз четвер, 2 жовтня 2026, 20:15, вечір, осінь».
3. Назви днів і місяців беруться з таблиць у коді, а не з системної локалі Mac. Годинник підміняється в тестах (функція, що повертає «зараз»).
4. **Остання розмова:** у промпт іде, коли був останній підсумок сесії (фаза 6), напр. «Востаннє ви говорили позавчора ввечері».

### Спогади по днях

1. **Спогад дня** — короткий текст від першої особи агента про один день: що він робив і бачив у Львові того дня і про що говорили в кімнаті, якщо розмова була.
2. **Генерується автоматично,** один раз на кожен минулий день, окремим викликом Gemini. На вхід: канон агента, дата, день тижня й пора року того дня, спогади попередніх днів (для зв'язності) і журнал розмов того дня.
3. **Журнал розмов дня:** кожен підсумок сесії (фаза 6) додатково дописується з часом у `state/<name>.days/YYYY-MM-DD.talk.md`.
4. **Правда і вигадка:** те, що було в кімнаті, береться **тільки** з журналу розмов. Вигадані епізоди дня стосуються лише самого агента й міста — без слів і дій власника чи іншого агента, яких не було (інакше спогади Ади і Бруно суперечитимуть одне одному).
5. **Коли:** після опівночі за `TIMEZONE` бот генерує спогад за вчора. На старті він доганяє пропущені дні (поки бот був вимкнений), але не далі ніж на `MEMORY_DAYS` днів назад.
6. **Зберігання:** `state/<name>.days/YYYY-MM-DD.md`, до `DAY_MEMORY_MAX_WORDS` (напр. 120) слів, атомарний запис. Спогад минулого дня **не переписується** — спогади стабільні.
7. **Промпт:** розділ «Твої спогади за останні дні» — останні `MEMORY_DAYS` (напр. 7) спогадів у хронологічному порядку, кожен з позначкою дня («вчора, середа, 1 жовтня: …»).
8. **Помилки:** якщо Gemini не зміг — день лишається без спогаду, спроба повториться пізніше, бот не падає.

### Порядок промпту

`system_instruction` = канон → місце, календар і час → спогади за останні дні → підсумок останньої сесії → правила формату відповіді. `contents` — як і раніше, останні `HISTORY_N` повідомлень.

### Налаштування

У `.env` / toml: `LOCATION`, `TIMEZONE`, `MEMORY_DAYS`, `DAY_MEMORY_MAX_WORDS`.

### DoD

- «Котра година?», «Який сьогодні день?» — правильні час, дата й день тижня у Львові.
- «Де ти?» — агент знає, що він у Львові.
- Після опівночі з'являються `state/ada.days/<вчора>.md` і `state/bruno.days/<вчора>.md`; на «Що ти робила вчора?» Ада відповідає зі свого спогаду, а якщо вчора була розмова, згадує і її.
- Бот був вимкнений 3 дні — на старті з'являються спогади за пропущені дні (не більше `MEMORY_DAYS`), старі файли не змінюються.
- У вигаданих епізодах немає слів і дій власника чи іншого агента, яких не було в кімнаті.
- Gemini падає під час генерації спогаду — бот живий, день догенерується пізніше.
- Юніт-тести без мережі (Gemini замоканий, годинник підмінений): дата й час українською (включно з переходом на літній / зимовий час), які дні треба згенерувати, «минулий день не переписується», порядок розділів промпту.

## 10. Фаза 8 — підрахунок токенів і звіт

Щоб бачити, скільки коштують розмови, кожен виклик Gemini записується з кількістю токенів, а окрема команда будує звіт.

### Облік

1. Після **кожного** виклику Gemini — відповідь, підсумок сесії (фаза 6), спогад дня (фаза 7) — агент бере `resp.usage_metadata` і дописує один рядок JSON у `state/<name>.usage.jsonl`.
2. Поля рядка: `ts` (час у `TIMEZONE`), `agent`, `kind` (`reply` / `summary` / `day_memory`), `model`, `prompt_tokens`, `output_tokens`, `total_tokens`, `ok`. **Без текстів** повідомлень, промптів і відповідей.
3. Кожен агент пише лише у свій файл — двом процесам не треба ділити один файл.
4. Якщо `usage_metadata` немає або в ньому бракує полів — рядок пишеться з `null`, бот не падає. Невдалий виклик пишеться з `ok: false`.
5. Облік не блокує розмову: помилка запису — лог, бот працює далі.

### Звіт

1. Команда: `uv run agents/usage_report.py [--days N] [--since YYYY-MM-DD] [--markdown]`.
2. Читає всі `state/*.usage.jsonl` і друкує таблицю по днях × агентах × видах викликів: кількість викликів, вхідні та вихідні токени, разом і орієнтовна вартість. Унизу — підсумки по агентах і загальний.
3. **Вартість** рахується за цінами з `.env`: `PRICE_INPUT_PER_1M`, `PRICE_OUTPUT_PER_1M` (USD за 1 млн токенів, з прайсу Gemini). У коді цін немає, бо вони змінюються. Якщо цін не задано — звіт без колонки вартості.
4. Пошкоджений рядок пропускається з попередженням; файлів немає — звіт каже, що даних немає.
5. `--markdown` друкує ту саму таблицю в markdown, щоб її можна було вставити в нотатки.

### Налаштування

У `.env`: `PRICE_INPUT_PER_1M`, `PRICE_OUTPUT_PER_1M`.

### DoD

- Після розмови в `state/ada.usage.jsonl` і `state/bruno.usage.jsonl` — по рядку на кожен виклик Gemini, з токенами й без текстів.
- `uv run agents/usage_report.py --days 7` показує виклики й токени по днях, агентах і видах, і орієнтовну вартість; суми збігаються з рядками у файлах.
- Звіт працює, коли файлів немає, коли вони порожні і коли є пошкоджений рядок.
- Юніт-тести без мережі: розбір `usage_metadata` (включно з відсутніми полями), агрегація, розрахунок вартості, пропуск пошкоджених рядків.

## 11. Фаза 9 — веб-панель на Mac

Щоб не тримати два термінали й не шукати файли в `state/`, на Mac працює локальна веб-панель. У ній агентів запускають і зупиняють, дивляться логи, пам'ять, токени і стан сервера.

### Як влаштована

1. Окремий процес у тому ж uv-проєкті: `uv run panel/app.py`, далі браузер на `http://127.0.0.1:8090` (`PANEL_PORT`).
2. Сервер — `aiohttp.web`: aiohttp уже є залежністю `matrix-nio`, тож нового фреймворку не треба. Сторінка — один HTML-файл з vanilla JS, без збирання й без CDN. Інтерфейс українською.
3. Панель слухає **тільки `127.0.0.1`** — з інших пристроїв у мережі її не видно.
4. Агенти працюють і без панелі: запуск із терміналу, як у фазі 3, лишається.

### Агенти

1. Для кожного агента панель показує стан (працює / зупинений), PID, час роботи й останню активність, а також кнопки **Старт**, **Стоп** і **Рестарт**.
2. **Старт:** панель запускає `uv run agents/agent.py agents/<name>.toml` в окремій сесії процесів, тож зупинка самої панелі агентів не зупиняє.
3. **Стоп:** SIGINT (агент встигає зробити підсумок сесії, фаза 6); якщо за 30 с процес не вийшов — SIGKILL.
4. **Один екземпляр:** на старті агент бере lock `state/<name>.lock` (flock) і записує туди PID. Другий екземпляр того самого агента — з панелі чи з терміналу — не стартує і пише зрозумілу помилку. Інакше дві Ади відповідали б двічі.
5. Агента, запущеного з терміналу, панель бачить за lock-файлом, показує як «працює» і може зупинити (SIGINT за PID).

### Логи

1. Агент завжди пише лог у `state/logs/<name>.log` (ротація: 1 МБ × 3 файли) і в консоль.
2. Панель показує останні 200 рядків логу кожного агента й оновлює їх кожні 2 с.
3. У логах, як і раніше, немає токенів, паролів і текстів повідомлень, тож їх безпечно показувати.

### Адміністрування

1. **Сервер:** індикатор, чи відповідає homeserver (`/_matrix/client/versions`), оновлюється кожні 30 с.
2. **Пам'ять (фази 6–7):** для кожного агента — підсумок останньої сесії і спогади по днях. Кнопка **«Забути останню сесію»** видаляє `state/<name>.memory.md` після підтвердження і лише тоді, коли агент зупинений (інакше він перезапише файл зі своєї пам'яті). Спогадів днів панель не змінює.
3. **Канони (фаза 6):** перегляд `agents/canon/*.md`, тільки читання — їх редагують у редакторі й комітять.
4. **Токени (фаза 8):** той самий звіт, що `usage_report.py`, — таблицею за останні 7 днів, зі спільним кодом агрегації.
5. **Налаштування:** чинні значення з `.env` і toml, тільки читання; усе, що схоже на секрет (`*_KEY`, `*_PASSWORD`, `*_TOKEN`), замасковане.

### Безпека панелі

1. Тільки `127.0.0.1`, CORS вимкнений.
2. Кожен запит перевіряє заголовок `Host`: лише `127.0.0.1:<порт>` або `localhost:<порт>` — захист від DNS rebinding.
3. Дії, що щось змінюють (старт, стоп, «забути»), — лише `POST` з `Origin` самої панелі, тож сторонній сайт у браузері не зможе натиснути кнопку за тебе.
4. Панель не виконує команд на Ubuntu-сервері.

### Налаштування

У `.env`: `PANEL_PORT`.

### DoD

- `uv run panel/app.py` → `http://127.0.0.1:8090` показує обох агентів зі станом; з іншого пристрою в мережі панель недоступна.
- Старт, Стоп і Рестарт працюють; після Стопу є свіжий підсумок сесії (фаза 6).
- Другий екземпляр агента не стартує ні з панелі, ні з терміналу.
- Агента, запущеного з терміналу, видно в панелі як «працює»; закриття панелі агентів не зупиняє.
- Логи видно, вони оновлюються; у них немає токенів, паролів і текстів повідомлень.
- Контейнер homeserver зупинений → індикатор сервера червоний.
- «Забути останню сесію» працює тільки для зупиненого агента і лише після підтвердження.
- Таблиця токенів збігається з `uv run agents/usage_report.py --days 7`.
- У налаштуваннях секрети замасковані.
- `POST` з чужим `Origin` або запит із чужим `Host` — відмова.
- Юніт-тести без мережі: супервізор процесів на фейкових процесах (старт, стоп, таймаут → kill), lock одного екземпляра, маскування секретів, перевірки `Host` / `Origin`, обробники API через тестовий клієнт aiohttp.

## 12. Безпека (підсумок)

| Загроза | Захист |
| --- | --- |
| Хтось реєструється на сервері | Реєстрація вимкнена після фази 2; токен тільки в `server/.env` |
| Хтось з інтернету | Порт 8008 не прокинутий у роутері; ufw — тільки `192.168.1.0/24`; федерація вимкнена |
| Хтось пише ботам (DM, інша кімната) | Allowlist у коді: тільки `ROOM_ID` + `{OWNER, інший агент}` |
| Витік ключів | `.env`, `server/.env`, `state/` — у `.gitignore`; токени й тексти повідомлень не логуються |
| Агенти спалюють кредити, балакаючи між собою | `MAX_BOT_TURNS`, `BOT_REPLY_P`, `max_output_tokens`; один виклик-підсумок на сесію; один спогад на день; звіт по токенах (фаза 8) показує витрати |
| Витік розмов | Підсумки, журнали й спогади днів — тільки в `state/` (у `.gitignore`); їхні тексти не логуються |
| Приватне в публічному репо | Канони комітяться — без секретів і приватних даних власника |
| Хтось керує агентами через панель | Панель тільки на `127.0.0.1`; перевірка `Host` і `Origin`; секрети в налаштуваннях замасковані |

HTTP без TLS у LAN — свідомий компроміс PoC: паролі йдуть відкритим текстом у домашній мережі. Перед будь-яким доступом ззовні — Tailscale (або reverse proxy з TLS).
