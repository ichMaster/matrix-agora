## Findings

### 1. 🟠 Writing first undoes `last_channel`
`agents/agent.py:706-730`. `maybe_private_nudge` loads the private state and awaits `private_reply`, which makes a
model call, TTS and an upload. It then saves that same object to record `count` and `sent_ms`.

**Scenario:** `last_channel=matrix`. While she composes a first line for Element, the owner writes in Telegram, and
`private_line` saves `last_channel=telegram`. The nudge's save then puts `matrix` back, so her next first line goes
to Element although he last wrote in Telegram. The same save also puts back a `room` that `_move_private_room`
changed in the meantime.

**Fix:** after a sent line, load the state again, add 1 to `count`, set `sent_ms`, and save that.

### 2. 🟠 A dead door stays open; a failed send counts as said
`agents/agent.py:749` (the poller returns on 401/404 but `self.telegram` stays set) and `:827-848` (`send_telegram`
ignores the results of `send_voice` and `send_message`).

**Scenario:**
- The token is revoked and `last_channel=telegram`. Every first line still goes to Telegram:
  - TTS is made and billed, and `count` goes up;
  - the line enters `private_history` and the session as if said;
  - the open Element room is never used.
- A 403 (the owner blocked the bot) has the same effect on every answer.

**Fix:** a `telegram_open` flag, cleared when the poller stops on a refusal, which `pick_door` reads.
`send_telegram` returns whether the text went out; when it did not, `private_reply` returns False and records
nothing.

### 3. 🟡 A message just after the start is read as backlog
`agents/agent.py:783`. Telegram dates are whole seconds, but `started_ms` keeps its milliseconds.

**Scenario:** the agent starts at 12:00:00.400 and the owner writes at 12:00:00.900. The date reads 12:00:00.000,
which is before the start, so the message becomes context and is never answered.

**Fix:** compare with the start floored to the second.

### 4. 🟡 A failure inside a batch replays it
`agents/agent.py:758-761`. The offset is saved only after `on_telegram` has handled the whole batch.

**Scenario:** an update in the middle of a batch raises, for example an `OSError` from `save_private_state` when
the disk is full. The poller backs off and fetches the same batch again. The earlier updates are answered twice and
their voice notes are sent to Deepgram twice, which breaks the rule that an update is never answered twice.

**Fix:** catch per update inside `on_telegram`, logged by type, so one bad update never replays the others.

### 5. 🟡 The Telegram side of the history is RAM only (deferred)
`agents/agent.py:591-612`, `:712`. `start_private` seeds the history from the Element room only.

**Scenario:**
- After a deploy, a Telegram answer is written against older Element lines; the earlier Telegram lines survive
  only through the summary.
- For an owner who uses only Telegram, the history is empty after a restart, so she does not write first until he
  writes.

This was noted when the issues were generated ("persisting Telegram lines beyond the session: v5.8's archive").

**Home:** v5.8. Its archive keeps both doors, and the private history can be seeded from it.

### 6. 🟡 Bot commands reach her prompt
`agents/telegram.py:83-94`. Telegram sends `/start` when the owner opens or restarts the bot. It arrives as his
text, so `Ich: /start` reaches the model and gets an answer, or sits in the backlog. A bot command in a persona's
transcript invites a reply that treats her as a bot, against the human-belief rule.

**Fix:** `allowed()` refuses a text that starts with `/` as `command`.

### 7. 🟡 A random `update_id` after a week of silence
`agents/telegram.py:97`, `agents/agent.py:760`. The Bot API documentation says that after a week without updates,
the next `update_id` is chosen at random. If it is below the stored offset, `getUpdates(offset)` confirms it without
returning it.

**Scenario:** the owner uses only Element for a week. From then on the Telegram door drops every message without a
trace, and the saved offset makes this outlast restarts.

**Fix:** `TelegramState` keeps `seen_ms`, the time of the last batch with updates. When it is more than 6 days old,
or unknown with an offset set, the poller asks without an offset: only unconfirmed updates come back, and the date
check still keeps old ones from being answered.

## Fixes applied

Each fix has a regression test, and each test was run without its fix to see it fail. Gates after every fix: lint ✓,
tests ✓ (1236 at the end), compose n/a (no `server/` change).

### #1 — writing first never undoes the door he switched to · 3665fd4
- **Change:** `maybe_private_nudge` reads the private state again after a sent line, then adds to `count` and sets
  `sent_ms`. A change of door or a moved room made while she was writing is kept.
- **Test:** `test_writing_first_never_undoes_the_door_he_switched_to_meanwhile`.

### #2 — a refused token closes the door; an undelivered line is never said · 2f37745
- **Change:** `telegram_open` is set with the bot and cleared when the poller stops on 401/404; `pick_door` and
  `maybe_private_nudge` read it. `send_telegram` returns whether the text went out. When it did not,
  `private_reply` logs `private: not delivered (telegram)`, returns False, and puts nothing in the history, the
  session or the count.
- **Tests:** `test_a_refused_token_closes_the_door_and_element_takes_the_lines`,
  `test_a_line_telegram_refused_is_never_counted_as_said`.

### #3 — a message sent just after the start is answered · d2aa507
- **Change:** the backlog check compares Telegram's whole-second date with the start floored to the second.
- **Test:** `test_a_message_sent_just_after_the_start_is_answered`.

### #4 — one failing update never replays its batch · a0b1b11
- **Change:** `on_telegram` handles each update on its own. A failure is logged by its type
  (`telegram: an update failed (<type>) — skipped`), and the batch's offset is still saved.
- **Test:** `test_one_failing_update_never_replays_the_batch`.

### #6 — bot commands never reach her prompt · 91d3d24
- **Change:** `allowed()` refuses a text that starts with `/` as `command`, before the backlog and the history.
- **Tests:** three new cases in `test_only_the_owners_private_text_or_voice_is_handled`: `/start`, `  /help me`,
  and `а/б тест`, which still goes through.

### #7 — a week-stale offset is dropped · 7335f4c
- **Change:** `TelegramState` gains `seen_ms`, the last batch that held updates. `poll_offset(state, now)` sends the
  stored offset only while `seen_ms` is known and at most 6 days old; otherwise it polls without one, so only
  unconfirmed updates come back. A v5.7.0 file with no `seen_ms` polls once without an offset, which is safe:
  everything handled was already confirmed.
- **Tests:** `test_a_stale_offset_is_dropped` (5 cases), the state round trip with `seen_ms`, and
  `test_after_a_week_of_silence_the_poller_asks_without_the_offset`.

**Architecture impact:**
- #7 changes the contract of `state/<name>.telegram.json`: it gains `seen_ms`. ARCHITECTURE §Data and state files
  is updated in the same commit, pinned by `tests/test_telegram.py`.
- #2 and #6 change behaviour that §Message flow describes only in general terms: a refused token closes the
  Telegram door, so Element takes every line; a bot command is ignored as `command`. No contract changes.

## What's solid

- **Authority.** `allowed()` (a private chat and the owner's numeric id) runs before the backlog, the history, the
  voice download and the model. Every send goes to `TELEGRAM_OWNER_ID`, never to an update's `chat_id`. A
  stranger's voice note is never downloaded.
- **Secrets.** Every Bot API call, the download, Deepgram and ElevenLabs log only a status or an exception type, so
  the token in the URL never reaches a log. The state files hold no text or id. The keys leave the environment
  before anything else runs. Only `kira` reads `kira.env`.
- **Resilience.** The poll loop catches everything but cancellation: a 429 waits, a 409 or a 5xx backs off, and
  only a 401/404 stops it, logged. The chat-action task is cancelled in `finally`.
- **Two doors.** Each answer reads the door when it starts, and the `_private_again` loop follows a change of door.
- **Persona.** The fixed lines read as a person's.
