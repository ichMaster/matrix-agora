## Findings

### 1. 🔴 An owner message is swallowed by an in-flight agent-to-agent reply
**Where:** [agents/agent.py](../../agents/agent.py) `on_message` (coalescing), `reply_later`, and the pre-send check in `reply`.

**Scenario:**
1. Ada is generating a reply to Bruno's B1 (`trigger="$b1"`).
2. During the Gemini call the owner writes «Адо, а ти?». Ada is chosen, but `_reply_pending` is set, so the message coalesces and `_pending_trigger` becomes `None`.
3. Generation ends. `reply()` re-checks the captured `"$b1"`: the latest message is now the owner's, so it drops the reply ("moved on").
4. Nobody answers the owner. This breaks R1's "never suppressed", and it is new in v4.1 (the pre-send R3).

The same thing happens when a newer agent trigger coalesces during generation.

**Fix:**
- `reply()` reports whether it sent.
- If it did not, and the pending trigger changed while it generated (something coalesced), `reply_later` runs once more with the new trigger and fresh context.

### 2. 🟠 The reservation of the owner's pending answers can turn the rate into a lock
**Where:** [agents/turns.py](../../agents/turns.py) `pending_answers`, `wave_frees_at`; `Agent.reserved`, `pause_until_window_frees`.

**Scenario:**
- A chosen replier that PASSes, fails or is offline never posts, so its slot stays reserved for all of `BOT_WINDOW_S`.
- `wave_frees_at` ignores reservations. When a reservation alone blocks, it returns `None`, and R4 schedules no resume.
- The agent also reserves a slot for **itself** after it PASSed. Example with two agents and `MAX_BOT_TURNS=2`: Ada PASSes on the owner's message, Bruno answers, and Ada's own phantom slot blocks her as Bruno's next speaker.

**Fix:**
- An agent never reserves for itself: whether it still owes an answer is local knowledge, not coordination.
- A reservation lapses `FALLBACK_S` after the owner's message (server timestamp). That is the point where the fallback takes over anyway, and it is no longer `BOT_WINDOW_S`.
- When a reservation is what blocks, `wave_frees_at` returns that lapse time, so R4 resumes.

### 3. 🟠 The fallback can double-answer, or be skipped for good
**Where:** `Agent.fallback_later`.

**Scenario:**
- **Double answer:** a slow chosen agent (Lumi at ~15 s, a cold Claude call) answers after the fallback started generating. The fallback still sends, so the owner gets k+1 answers.
- **Skipped for good:** if the agent is busy at the 30 s mark, the fallback is dropped and never retried.

Both are latent with two agents and k=2 (no fallback ever fires).

**Fix:** re-check `fallback_due` right before sending. While the agent is busy, re-arm (a few short retries) instead of giving up.

### 4. 🟡 The group address matches ordinary sentences
**Where:** `GROUP_RE` in [agents/turns.py](../../agents/turns.py).

**Scenario:** «я кожен день гуляю, а ти?» and «прочитав всі новини, що думаєш?» each count as "everyone". With N agents, that means N answers.

**Fix:** match only in an addressing position:
- at the start of the message;
- right before `,`, `!`, `?` or the end;
- or «ви всі» / «вам усім».

Drop «кожного», which is not in the spec.

### 5. 🟡 An unreadable agent TOML crashes the panel
**Where:** `load_member` in [agents/roster.py](../../agents/roster.py).

**Scenario:** a directory, a permission error or a non-UTF-8 file raises a raw `OSError` or `UnicodeDecodeError` past `Registry()`. The pre-v4.1 panel caught any `OSError`.

**Fix:** turn `OSError` and `UnicodeDecodeError` into `RosterError`.

### 6. 🟡 `rank` and weight edge cases
**Where:** `rank` in [agents/turns.py](../../agents/turns.py); `parse_member` in [agents/roster.py](../../agents/roster.py).

**Scenario:**
- `(x + 1) / (2**64 + 1)` rounds to exactly 1.0 for the top ~1024 digest values, so `log(1.0)` is 0 and the score divides by zero. The odds are about 5e-17, so this is theoretical.
- A weight of `nan` passes validation and breaks the sort.

**Fix:**
- `u = ((x >> 11) + 0.5) / 2**53`, which is exactly representable and always strictly inside (0, 1).
- Require `math.isfinite(weight)`.

### 11. 🟡 Tests that can't reach the races — DEFER → cleanup
**What the simulation lacks:** it has no generation latency, no coalescing and no PASS. The agent-level R3 tests use synthetic timestamps against the real clock, so only "is it the latest" is exercised.

**What changes now:** #1–#3 get explicit interleaving tests. Making the simulation more realistic is cleanup.

## What's solid
- **The allowlist** is roster-derived and guards every reply path. `resume_later` and `fallback_later` are spawned only after it passes, and `decide_reply` re-checks roster membership.
- **`rank`** uses `hashlib` and is the same across processes and independent of roster order. R1 and R2 are deterministic, so every agent computes the same chosen set and the same single next speaker.
- **Event ids** are the same in the backfill and in live events, and `last_owner` is seeded from the backfill.
- **Personas are unchanged.** For Ada and Bruno every capability is on, so their prompt order, summaries, journal, world line, today block, plans and chronicle are as before.
- **The responder** makes one Gemini call per reply, so usage is never double-counted. `MAX_TOKENS` is mapped.
- **The panel's** auth, 404s and routes are unchanged. No new secrets or texts appear in logs. `run-agent.sh` checks the name against the registry.

## Architecture impact

These notes are recorded for the next `/generate-issues` and `/reconcile-issues`, and ARCHITECTURE.md already reflects them.
- **§Turn-taking R3:** a message that coalesces into a pending reply during generation gets its own pass when the stale reply is dropped. An owner message is never swallowed.
- **§Turn-taking, the wave:**
  - an agent never reserves a slot for itself;
  - the reservation of the owner's pending answers lapses `FALLBACK_S` after the owner's message, not with the window;
  - R4 resumes at that lapse.
- **§Turn-taking R1:** the group address counts only in an addressing position.
- **§Turn-taking, the fallback:** it re-arms when the agent is busy and re-checks before sending.
- **The ranking draw:** it is `(x + 0.5) / 2**52` over 52 bits of the sha256. The orders differ from the pre-fix draw for the same event ids. No contract pins concrete orders.
