## Findings

### 1. 🟡 A missing look file is only an INFO note — `agents/agent.py:590`

**Failure scenario:** the canon on the host lacks `kira.look.md` (a deploy from a Mac without it, a typo in the name,
an unreadable file). Кіра starts with `photos: 21 faces, no look file` at INFO, and every selfie and кружечок frame is
drawn without «She never wears makeup» — the owner's v5.25 rule is gone and nothing stands out in the log. v5.17's
review #3 met the same shape («photos: 0 faces» at INFO went unnoticed on the first deploy) and made it a WARNING.
**Fix:** log the missing look file as a WARNING of its own («photos: no look file — her selfie has no look»); a test
that the level is WARNING and that a present file logs none.

### 2. 🟡 The seed command without its required args — `specification/ARCHITECTURE.md:489`, `agents/facts.py:14`

**Failure scenario:** the owner follows §Memory's «`python -m agents.facts seed [--dry-run]`» (or the module
docstring) for Устина's first facts in v6.3; argparse stops with a usage error. Harmless, but the docs point at a
command that no longer runs as written.
**Fix:** both say `seed --agent <localpart> --name <her name> [--dry-run]`. (ROADMAP v5.8's lines are a completed
phase's record and stay as they are.)

### 3. 🟡 `.DS_Store` reaches the host — `server/deploy.sh` (the canon rsync)

**Failure scenario:** the deploy's dry run listed `<f+++++++ .DS_Store` under the canon: Finder's metadata file of
`agents/canon/` on the Mac goes to `~/matrix-agora/canon/` (0600). Nothing reads it; it only adds noise to the
deploy's change list. Pre-existing — not v6.2's change.
**Fix (later):** `--exclude .DS_Store` on the canon rsync. **Home:** backlog.

### 4. 🟡 One process cannot prove two tokens — `tests/test_two_companions.py`

**Failure scenario:** each bot's token and owner id are read from the process environment (`TELEGRAM_BOT_TOKEN`),
and in production each companion's container reads its own `server/<name>.env`. A single-process test shares one
environment, so its Telegram check shows only that the state files differ. A compose file that gave Устина's service
`kira.env` would not be caught.
**Fix (later):** v6.3 adds her compose service; its test pins that `ustyna` reads `ustyna.env` and never `kira.env`,
and `kira` never `ustyna.env` (as `test_compose.py` pins `kira.env` today). **Home:** v6.3.
