## Findings

### 1. 🟠 The panel's today tag rejects the event count
`panel/memory.py:30`

AGORA-129 changed the today block's tag to carry the day's event count (`<!-- 2026-10-28T14 e2 -->`), so a new event
refreshes the block within the hour. The agent's readers match only the prefix `<!-- 2026-10-28T`, so they are
unaffected. The panel's `TODAY_TAG` (`^<!--\s*(date)T(\d{2})\s*-->`) does not match the new tag.

- **Failure scenario:** an event falls at 10:00, and the block is rebuilt as `<!-- …T10 e1 -->`. Until midnight the
  memory view's `today` is `null`: her card says «No today block yet» and the Today tab is empty, while the block
  exists and reaches her prompts.
- **Fix:** accept an optional ` eN` in `TODAY_TAG`. Add a test with an event-count tag.

### 2. 🟠 A story event re-entered every watcher tick
`agents/life.py` (`_split_events`), `agents/agent.py` (`_events_tick`)

`_events_tick` enters a due story event unless the day file already holds one with the same source and text. The day
file's text is normalized by `parse_day` (`" ".join(body.split())`), but the canon's text is kept raw.

- **Failure scenario:** a canon line has a double space or a tab inside its text. The comparison never matches, so
  the event is appended again at every watcher tick (≤ 30 s), about 1,800 times a day. The copies reach «Сьогодні»,
  the day memory and the panel.
- **Today's canon:** has no such line, but one edit is enough.
- **Fix:** normalize the event text in the parser. Add a test with a double-spaced canon line ticked twice.

### 3. 🟠 A known event is in no plan on its own day
`agents/life.py` (`known_ahead`)

`known_ahead` takes `today < e.date`, so the plans see a known event only before its day.

- **Failure scenario:** the day plan for 6 November, built at the day's start, never mentions the showing to the
  planetarium's director. The week plan made that Monday misses that Monday's event too. The event then appears only
  as a fact in the day file at the first waking tick.
- **Fix:** take `today <= e.date`, labelled «сьогодні».

### 4. 🟠 A story event falls at the first waking tick
`agents/agent.py` (`_events_tick`), `agents/life.py`

Her story's events of the day are entered at the first tick inside `EVENT_HOURS`, normally 08:00. «Сьогодні» and the
day memory present the day file as what really happened («це справді було»).

- **Failure scenario:** the premiere under the dome (an evening) or the night watch of the Leonids is written
  `[08:00] …` and told in her talk from 08:00 on as already done («Сьогодні вже: прем'єра…»). With #3 fixed, the day
  plan would also hold it as still ahead, so her prompts would contradict each other.
- **Fix:** an optional time in the line, `- YYYY-MM-DD HH:MM · known|surprise · text`.
  - A timed event enters at the first tick at or after its time; an untimed one at the first tick, as before.
  - A time outside `EVENT_HOURS` is warned about at startup, since it would never enter.
  - The plans show the time.
  - Kira's private canon gets times for the events where the hour matters.
- **Contract:** the life-story format in ARCHITECTURE.md and the parser's test.

### 5. 🟡 The visibility rule is stale
ARCHITECTURE.md §Canon, CLAUDE.md

Both still say that «only the plan generator sees the next chapter». Since AGORA-127 the event call sees the next
chapter's opening too, as a silent direction; §Memory documents this, so the two sections disagree.

- **Fix:** name both generators in both places.

### 6. 🟡 A marker comment inside a generated text
`agents/events.py` (`parse_day`)

`_ROLLED_RE` and `_NEWS_RE` scan the whole day file, event bodies included.

- **Failure scenario:** a generated event holding `<!-- rolled 15 -->` would mark hour 15 as rolled. The event call
  never asks for markup, so this is unlikely.
- **Fix:** reject a text with `<!--` or `-->` in `event_ok`.
- **Home:** backlog.

### 7. 🟡 The news weave fills its cap on most days
`agents/citynews.py` (`LVIV_BOOST`), the default `CITY_NEWS_P`

In a real sample, 14 of 50 items (eight hours of the feed) name Lviv. Zaxid.net is a Lviv outlet. About 150 items a
day give roughly 42 × 0.05 + 108 × 0.01 ≈ 3 expected hits, so the cap of 2 is reached on about four days in five.
News would then be close to half of her events, which is more often than «rarely».

- **Home:** this is the owner's tuning in the panel («Життя»): `CITY_NEWS_P` 0.003 would give about one a day, and
  `CITY_NEWS_MAX` 1 would cap it at one. Watch the first days before changing the default.

## What's solid

- **The hidden list stays hidden.** `### Події` is cut out of `Chapter.body` before any prompt reads it.
  - A surprise is entered only on its date and never reaches a plan.
  - `events_for_prompt` is the only way an event reaches a prompt: the time and the text, never a kind, a source, a
    link or a marker.
- **The hourly roll is restart-safe.** The hour is marked rolled before the call, so a restart never rolls it twice,
  and a failure backs off without blocking the watcher.
- **The truth guard.** It rejects the Ich forms, every member's name forms and the banned words, with one
  regeneration and then nothing.
- **The feed is handled defensively.**
  - A DOCTYPE or an entity is refused, and the response is capped in size.
  - Only https links are kept, and a failed fetch is retried in an hour without blocking the event roll.
  - The state file is atomic and 0600.
- **The panel.** The tab escapes every text, links only https with `noopener noreferrer`, and degrades to «Events
  unreadable» instead of a 500.
- **No regressions for the others.** A member without `events` sends byte-identical requests (pinned), and the
  network fixture keeps every test offline.

## Architecture impact

- **The today block's tag** may carry ` eN`, the day's event count. Every reader accepts it: the agents match the
  prefix, the panel matches `TODAY_TAG`.
- **The life-story format** (a contract): an event line is `- YYYY-MM-DD[ HH:MM] · known|surprise · text`.
  - A timed event falls from its time.
  - `LifeEvent` carries `time`.
  - It is pinned by `tests/test_life_events.py`.
- **The plans' known events** run from today, not from tomorrow.
- **The visibility rule:** the event call joins the plan generator in reading the next chapter's opening.
